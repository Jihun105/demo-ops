# 업무 데이터와 백업

## 공유 모드 자료와 복구

아래 로컬 DB 절차는 아직 전환하지 않은 기존 형식에 해당합니다. 공유 모드의 확정 저장은 서버 명령 한 트랜잭션으로 고객·묘지·금액·작업과 공개 조회 사본을 갱신합니다. 고객 ID와 묘지 ID는 예약·영구 삭제 이후에도 다시 사용하지 않습니다. 조회 사본은 userData/desktop-shared의 회사별 cache.db, 미전송 입력과 요청 번호는 같은 회사 안의 계정별 actors 폴더에 보관됩니다. 다른 계정의 초안은 화면에 복원하지 않습니다.

Earth는 먼저 보이지 않는 후보/번호를 준비하고, 원본 해시와 업로드 완료를 확인한 뒤 주소·고객 버전·이전 연결을 비교하여 확정합니다. 원본 업로드만으로 연결을 바꾸지 않습니다. 실패하면 이전 연결이 유지됩니다. 확정 후 또는 영구 삭제 후 서버의 현재 참조가 없는 버전만 폐기하며 R2 정리는 별도 재시도 작업입니다. 로컬 원본 정리는 서버의 폐기 해시와 현재/미완료 원본 참조를 비교합니다. 같은 이름에 다른 내용을 저장한 파일은 제거하지 않습니다. 24시간 미확정 후보는 정리 대상으로 전환됩니다.

고객 상세의 **현재 원본 열기**는 서버가 허용한 현재 버전만 받습니다. 서명된 임시 URL로 받은 바이트의 크기·SHA-256을 검증하고, 받은 동안 현재 연결/회사/계정이 바뀌지 않았는지 다시 확인합니다. 검증된 사본은 회사별 조회 DB 옆 `.demo-earth/originals`에 보관해 Google Earth로 엽니다. 서버 연결·고객 값은 변경하지 않고 URL·로컬 경로는 고객 DB에 저장하지 않습니다.

전환 전에 고객 DB·field.db·지도 DB·현재 연결된 KML/KMZ를 무결성 확인한 개인 폴더에 보관합니다. 현재 연결 원본은 기존 버전 ID로 업로드 완료를 확인한 뒤에만 공동 모드를 활성화합니다. 업로드/응답 실패 시 원본 DB를 변경하지 않고 같은 버전으로 재시도합니다. 서버도 ready 상태·회사·manifest·폐기 여부를 검증하며 확인되지 않은 현재 연결은 전체 이전을 롤백합니다. 과거 원본이 이미 최신 파일 정리로 제거되었다면 그 바이트를 새로 복원하지 않고 버전 메타데이터를 유지합니다. 전환 이후 복구는 먼저 최신 공유 변경/이벤트를 내보내야 합니다. 예전 PC DB를 서버 위에 다시 올리는 복구 방식은 사용하지 않습니다.

## 고객 삭제 목록

고객 삭제는 `company.db`의 `customers.deleted_at`에 UTC ISO 시각을 기록하는 방식입니다. 고객 미연결 묘지는 `graves.deleted_at`을 사용합니다. 고객에게 연결된 묘지는 고객의 삭제 상태를 따르며, 묘지의 원본 행을 일괄 변경하지 않습니다. 복원은 해당 삭제 표시만 `NULL`로 되돌립니다. 기존 DB는 첫 삭제·복원 전에 백업한 뒤 없는 컬럼만 추가합니다. 조회만으로 스키마를 변경하지 않습니다.

전체 snapshot과 서버의 원본 catalog는 삭제 표시와 원본 자료를 유지해 작업·입금·사진 연결에 사용합니다. 일반 고객 목록, 신규 영업/보고 검색, 지도·Excel은 삭제 자료를 제외합니다. 직원용 서버 조회도 삭제 자료를 제외하며, 삭제 자료에 새 GPS 요청·승인을 할 수 없습니다. 이 방식은 복원을 위한 보관이며 개인정보를 영구 파기하는 기능은 아닙니다.

삭제 목록 상세의 **영구 삭제**는 삭제 상태·최신 revision을 검증하고 자동 백업을 만든 뒤, 하나의 트랜잭션으로 고객과 연결된 묘지·연도별 금액·로컬 연간 작업·어스 위치 및 버전을 제거합니다. 미연결 묘지는 그 묘지만 제거합니다. 알 수 없는 관련 테이블에 연결 자료가 있으면 삭제를 취소하고 원본을 보존합니다. 이후 새 고객·묘지를 만들 때 삭제된 ID를 재사용하지 않아 과거 기록이 새 고객에게 연결되지 않습니다. 변경된 최신 catalog는 기존 자동 공유 흐름으로 전달합니다. 영구 삭제에 한해 현재 앱이 지정한 Google Earth 폴더의 KML·KMZ도 제거합니다. DB의 경로 문자열은 실행하지 않으며, 같은 회사·묘지의 유효한 원본 manifest와 SHA-256이 일치하는 일반 파일만 처리합니다. 다른 묘지가 참조하는 파일명은 대소문자를 포함해 공유 여부를 확인하여 보존하고, 내용 변경·미검증 원본·심볼릭 링크도 삭제하지 않습니다. 파일 내용은 DB 백업 옆 `<backupPath>.earth-files`에 보관한 뒤 같은 Google Earth 폴더 내부의 전용 임시 디렉터리로 이동합니다. DB COMMIT 전에 실패하면 기존 파일명을 덮어쓰지 않고 원위치 복원을 시도합니다. SQLite 자동 롤백이나 명시적 롤백 실패도 파일 복원을 건너뛰지 않습니다. 성공 후 임시 파일을 정리하고 삭제 개수·보존 사유를 화면에 반환합니다. 갑작스러운 프로세스 종료 시 남은 임시 파일과 파일 백업은 보존됩니다.

영구 삭제 후 앱의 삭제 목록에서 복원할 수 없습니다. 별도 저장소의 청구·입금 이벤트, 작업 보고·사진·지도 캐시·앱 내부·클라우드의 어스 원본 보관 사본과 자동 백업은 유지하므로, 과거 사본까지 파기하는 기능은 아닙니다.

## 신규 영업 거절 기록

신규 등록의 거절 기록은 `customers.registration_status='declined'`로 보관하며, 일반 등록은 `registered`입니다. 기존 DB에 열이 없으면 일반 등록으로 읽고, 첫 신규 등록·거절 저장 때 검증된 백업 후 같은 트랜잭션에서 열을 추가합니다. 고객·묘지·금액·요구사항·어스 위치와 상태를 함께 저장하므로 중간 실패 시 모두 취소합니다. 전체 snapshot에는 거절 기록을 유지하고 일반 고객·영업·작업·지도·Excel에서는 제외합니다. 연도별 `annual_work.status='declined'`(미진행)와는 별개입니다.

## 실제 자료 저장 위치

앱은 Electron의 운영체제별 `appData` 아래 `Demo` 폴더를 사용합니다. 소스 실행과 설치본 모두 같은 규칙이며, 프로젝트의 `data/`나 `.local-state/`를 기본 자료로 읽지 않습니다.

- macOS: `~/Library/Application Support/Demo`
- Windows: `%APPDATA%\Demo` (일반적으로 `C:\Users\사용자\AppData\Roaming\Demo`)

아래 경로는 이 앱 전용 폴더를 기준으로 합니다.

| 경로                                                                    | 내용                                                     |
| ----------------------------------------------------------------------- | -------------------------------------------------------- |
| `data/company.db`                                                       | 고객·묘지·연도별 금액, `demo_workspace`의 고정 회사 ID   |
| `data/작업자료/`                                                        | 작업 표 DB와 Excel·Numbers 원본·사본                     |
| `data/.demo-mobile/field.db`                                            | 청구·발송·입금 기록, 연결 설정, 동기화 진행 상태         |
| `data/.demo-map/`                                                       | 현장/공공 좌표와 만료 시각이 있는 Google 임시 캐시       |
| `data/.demo-backups/`                                                   | 고객 자료 변경 전 복구 사본                              |
| `data/source-files/`, `data/import-reports/`, `data/location-evidence/` | 원본 자료, 가져오기 점검, 좌표 조사 근거                 |
| `data/엑셀내보내기/`                                                    | 사용자가 내보낸 자료                                     |
| `auth-settings.json`, `database-location.json`                          | 회사 연결 설정과 선택한 DB 위치                          |
| `IndexedDB/`, `Local Storage/` 등                                       | 앱 내부 창의 초안·사진·상태. 임의로 초기화하지 않습니다. |

저장된 DB 위치가 사라졌거나 설정이 손상되면 앱은 다른 DB를 임의로 열지 않고 오류를 표시합니다. 위치 설정이 없을 때만 앱 전용 폴더의 `data/company.db`를 사용합니다. DB만 옮겨도 회사 ID는 유지되지만 청구·입금 기록과 작업 자료는 별도이므로 관련 폴더도 함께 옮겨야 합니다.

## 개발 폴더에서 최초 이전

2026-10-10 개발 폴더의 `data`, `.local-state`, `.demo-backups`를 개발 폴더 밖에 백업하고 파일별 SHA-256과 SQLite 무결성을 확인한 뒤 앱 전용 데이터 폴더로 옮겼습니다. 이전이 끝나 일회성 이전 도구는 삭제했습니다.

현재 맥의 이전 백업은 `~/Library/Application Support/Demo Backups/data-move-20261010`에 보관합니다. 같은 디스크의 로컬 백업이며 기기 고장·분실에 대비한 외부 백업은 아닙니다. 고객 DB의 일반 자동 백업은 아래 보관 규칙을 적용합니다. 이 전체 이전 백업은 자동 정리하지 않습니다.

## 회사 Windows 컴퓨터로 이전

프로그램 설치 파일에는 실제 고객 자료를 포함하지 않습니다. 양쪽 앱을 종료하고 업무 자료 `data` 폴더를 대상 컴퓨터의 `%APPDATA%\Demo\data`에 옮깁니다. 기존 데이터가 있다면 덮어쓰지 말고 먼저 백업합니다. `auth-settings.json`에는 공개 연결 설정만 보관하며 필요한 경우 함께 이전합니다. 맥의 절대 경로가 담긴 `database-location.json`은 Windows에 복사하지 않습니다. 새 위치의 기본 DB를 사용하고 다시 로그인합니다.

맥의 Chromium 프로필 전체를 Windows에 복사하지 않습니다. 미전송 초안이나 로컬 사진이 있다면 이전 전에 처리를 완료하거나 별도로 보관해야 합니다. 서버와 동기화된 자료, R2 공유 사진은 기존 회사 계정으로 연결합니다. Google 임시 캐시는 장기 백업에서 제외하고 새 기기에서 재조회합니다. 같은 회사 자료를 두 PC에서 동시에 수정·게시하지 않습니다. Windows 설치본과 실제 기기에서의 이전 검증은 아직 별도 단계입니다.

## 연간 영업 확인과 작업

신규 고객 등록의 금액은 등록 연도의 묘지별 `payments`에 `kind='annual'`로 저장합니다. 고객 요구사항은 기존 `customers.memo`, 고객 특이사항은 `customers.special_notes`를 사용합니다. 신규 등록·전체 고객 목록·고객 상세·영업 확인에서 같은 두 항목을 읽고 저장하며 연도가 바뀌어도 유지합니다. 전체 고객 표에서는 두 메모 컬럼을 표시하지 않고, 행을 더블클릭하면 고객 상세에서 확인·수정합니다. 이전 DB는 조회만으로 변경하지 않으며 최초 등록·상세 수정·영업 저장 시 백업 후 같은 트랜잭션 안에서 특이사항 컬럼을 추가합니다. 기존 연간 메모 중 가장 최근의 비어 있지 않은 내용을 고객 특이사항의 초기값으로 가져오고 원래 연간 기록은 보존합니다. 항목을 보내지 않는 이전 편집 요청은 기존 메모를 유지하고, 명시적으로 빈칸을 저장하면 해당 메모를 비웁니다. 일반 신규 등록은 현재 연도의 `annual_work`에 진행 상태를 함께 생성하며, 거절 등록은 연간 작업을 만들지 않습니다. 신규 등록의 고객·묘지·금액·요구사항·특이사항·진행 작업은 같은 트랜잭션과 저장 전 백업으로 보호합니다.

작업 관리의 영업 확인은 전체 또는 지역을 선택한 뒤 올해 전화 결과를 아직 저장하지 않은 고객을 한 명씩 보여줍니다. 저장한 고객은 결과와 관계없이 영업 확인에서 제외하고 작업 관리에서 수정합니다. 아직 기록하지 않은 고객의 전화 결과는 연락 X입니다. `company.db`의 `annual_work`에 연도·고객 ID·대표 묘지 ID·전화 결과·특이사항·작업 기한을 저장합니다. 전년도 금액은 대표 묘지의 `payments` 중 전년도 `annual` 기록에서 읽고, 올해 입력 금액은 올해 `annual` 기록에 저장합니다. 영업 확인에서 요구사항·특이사항을 수정하고 저장하면 고객 DB와 고객 상세에 반영됩니다. 연간 메모는 저장 당시 특이사항을 보관합니다. 금액·전화 기록·두 고객 메모는 같은 트랜잭션·백업으로 보호하며 금액과 메모 변경도 revision 충돌 검사에 포함합니다. 메모와 기한은 비울 수 있습니다. 올해 금액 기록이 없으면 빈칸을 허용하고, 기존 금액은 0으로 변경할 수 있습니다. 조회만 할 때는 새 테이블이나 백업을 만들지 않습니다.

전화 결과를 한 번이라도 저장한 고객은 진행·미진행·연락 X에 관계없이 올해 작업 관리와 작업 확인에 들어갑니다. `readRegisteredWork`는 이 저장 목록을 읽고, `readAnnualWork`는 그중 진행 건을 현장 공유 작업 목록으로 읽습니다. 아직 결과를 저장하지 않은 고객은 기본 연락 X로 영업 카드에만 표시합니다. 재저장·미진행 전환·진행 복귀에서도 `annual:<UUID>` 작업 키가 유지됩니다. 고객 한 명당 연간 작업 한 건이며, 여러 묘지가 있으면 처음에는 활성 묘지 중 ID가 가장 작은 묘지를 대표로 사용하고 이후 연결은 유지합니다. 주소에서 지역을 구분하며 연도 경계는 한국 시간 기준입니다. 작업 기한은 최대 200자의 문자열로 그대로 보존하고 기존 날짜 문자열도 유지합니다. 지역별 작업 순서를 정하는 에이전트는 후속 단계입니다.

새 작업 목록은 기존 엑셀 행에서 만들지 않습니다. 이전 `작업자료` 폴더의 원본·사본·시트 DB와 과거 금융 이벤트는 삭제하지 않습니다. 현재 작업 관리 화면에는 영업 확인·작업 관리·작업 확인을 표시합니다. 작업 관리의 등록 열은 진행·미진행·연락 X 결과를 표시하고 검색과 결과 필터를 함께 사용합니다. 상세 수정은 최신 영업 조회의 연도·고객 ID·작업 키·revision을 확인하고 같은 저장 경로로 처리합니다. 작업 확인은 작업 순서 설정을 마쳐 저장한 시트만 표시하고, 선택한 시트의 방문 번호와 문자·입금 상태를 조회합니다. 진행 기록만으로 전체·지역별 시트를 자동 생성하지 않으며 구분 열은 빈칸으로 표시합니다. 원본 묘지 구분과 현장 catalog의 지역·번호 검색 값은 보존합니다.

## 청구 금액과 실제 입금의 구분

`company.db`의 `payments`는 기존 테이블 이름을 유지한 **연도별 청구 기준 금액**이며, 실제로 받은 돈을 뜻하지 않습니다. 문자 발송에 성공한 올해 청구 금액은 고객 DB의 올해 금액에도 반영합니다. 실제 청구 원본·발송 결과·입금·입금 취소는 `.demo-mobile/field.db`의 별도 이벤트입니다. 예를 들어 8만 원을 청구하고 5만 원을 받았다면 올해 금액은 8만 원, 입금 금액은 5만 원, 남은 금액은 3만 원입니다. 나머지 3만 원을 받아야 입금 완료가 되며 입금을 취소하면 다시 계산합니다.

같은 회사의 청구는 저장된 `customerId`와 `graveId`로 현재 고객·묘지에 연결합니다. 두 ID의 소유 관계도 확인하므로 다른 고객의 묘지에는 반영하지 않습니다. 이름이나 주소를 수정해도 이 ID는 유지되고, 과거 청구의 이름·주소·문자 본문은 발송 당시 내용으로 남습니다. 입금은 `claimId`로 해당 청구에 연결하며, 분할 입금이나 재수신된 같은 이벤트를 중복 계산하지 않습니다.

연간 작업 확인의 고객 연결은 저장한 고객 ID·묘지 ID가 기준입니다. 이름이나 주소가 바뀌어도 다른 고객에게 다시 추정해 붙이지 않습니다. 해당 작업 키의 청구는 발송일이 다음 해여도 작업 대상 연도의 금액과 입금 상태에 연결합니다. 진행 취소는 활성 작업만 제외하며 기존 청구·실제 입금 기록을 지우지 않습니다. 예전 엑셀 작업 연결 모듈은 명시적인 `task_linked`, 청구 ID, 유일한 주소·성함의 순서로 과거 기록을 처리합니다. 기존 ID가 사라지거나 여러 고객으로 충돌하면 **연결 확인 필요**로 표시하고 중복 합산하지 않습니다.

고객 화면·엑셀에는 전년도와 올해 금액을 표시하고, 작업 확인은 올해 금액만 표시합니다. 연간 영업 저장 시 새 테이블을 추가하지만 기존 고객·묘지·청구 원본을 다시 쓰지 않습니다.

## Google Earth 위치와 원본 보관

`earth-kml.cjs`는 KML/KMZ의 Point·Polygon을 검증하고 WGS84 경계와 내부 대표 지점, 구면 근사 면적을 계산합니다. 가져오기 팝업은 점 또는 다각형 하나가 있는 파일만 받아 대표 좌표와 계산 면적(근사값)을 표시합니다. 여러 위치가 있는 파일은 Google Earth에서 위치를 하나씩 별도 파일로 저장해 가져옵니다. 구조화 데이터에는 고도·스타일·설명·외부 링크·위성사진을 추출하지 않습니다. 원본 파일의 바이트는 그대로 보관하므로 KMZ에 이미 포함된 내용도 원본에는 남습니다. 파일·XML·압축 해제 크기를 제한하며 DTD와 외부 엔티티를 거부합니다. 렌더러가 보낸 면적·대표 좌표는 신뢰하지 않고 저장 직전에 geometry로 다시 계산합니다.

`earth-store.cjs`는 `company.db`의 `grave_earth_locations`에 묘지 ID·확인 당시 주소·`source='google_earth_kml'`·이름·파일명·선택적 `source_folder`·geometry JSON·대표 좌표·면적·확인 시각을 저장합니다. `source_folder`는 저장 폴더의 단일 이름이며 공용 폴더에서는 `Google Earth`입니다. 절대경로나 경로 이동 표현을 허용하지 않습니다. 공용 폴더 전환 후에도 기존 폴더명·원본 파일명·확인 시각과 버전의 가져오기 시각을 보존합니다. 최초 저장 전 검증 백업 후 트랜잭션 안에서 테이블을 만들거나 해당 열을 추가합니다. 읽기만 할 때는 DB를 변경하지 않으며 구형 레코드의 revision을 유지합니다. 기존 고객 저장은 주소와 `expectedRevision`으로 충돌을 막고, 신규 등록은 고객·묘지 생성과 같은 트랜잭션에 저장합니다.

현재 주소와 일치하는 `grave.earth` 요약만 고객 catalog에 포함합니다. 요약은 출처·주소·대표 좌표·근사 면적·확인 시각·선택적 버전 ID/해시이며 geometry·원본 경로·파일명은 공유하지 않습니다. `earth-sharing.sql`은 직원 자료에도 같은 허용 필드만 제공합니다. 휴대폰/데스크톱 지도는 승인한 현장 GPS → 어스 좌표 → 기존 필지/주소 좌표 순서로 표시합니다. 주소가 바뀌면 원래 기록은 보존하지만 공유 요약과 지도 적용에서 제외합니다. 기존 고객에 다각형을 가져오면 계산 면적에서 환산한 평수를 같은 저장 트랜잭션에서 갱신하며, 점 파일은 기존 평수를 유지합니다. 로컬 신규 등록은 사용자가 최종 확인한 평수를 유지합니다.

`earth-archive.cjs`는 안정적으로 읽어 파싱한 정확한 KML/KMZ 바이트를 DB 옆 `.demo-earth/originals/<sha256>.<확장자>`에 보관합니다. 렌더러에는 DB별 불투명 토큰을 주고 저장 시 메인이 원본 선택과 해시를 다시 검증합니다. 팝업을 닫아도 등록 전 토큰은 유지하되 로그아웃·DB 변경·페이지 재로드에서는 폐기합니다. 신규 고객/어스 위치와 `grave_earth_versions`의 변경 불가 manifest·업로드 대기를 한 트랜잭션으로 저장합니다. 같은 원본과 선택을 다시 저장하면 중복 버전을 만들지 않습니다. 가져오기를 취소하면 세션 토큰을 해제하고, 등록에 적용한 원본만 초안 보호 대상으로 유지합니다. 새 묘지 원본 저장이 완료되면 현재 연결·같은 폴더의 다른 DB·활성 가져오기에서 쓰지 않는 검증된 이전 원본을 `.demo-earth/originals`와 앱의 Google Earth 폴더에서 정리합니다. 내용이 바뀐 파일·심볼릭 링크·알 수 없는 파일은 유지합니다. DB 백업과 영구 삭제 복구용 파일 백업은 별도로 유지하며, 미등록 가져오기만으로 만든 캐시는 이 교체 정리 대상이 아닙니다.

기존 회사 동기화는 catalog/청구 자료를 먼저 처리하고, `earth-upload.cjs`가 현재 묘지 연결의 최신 대기 원본만 `backend.earth` 계약으로 보냅니다. R2 임시 업로드 → 서버 크기·SHA-256 검증 → 최종 원본과 manifest 저장 → DB ready 순서입니다. 성공한 버전·해시가 일치해야 로컬에 uploaded를 기록합니다. 업로드 상태 변경은 편집 revision을 바꾸지 않습니다. 실패하면 대기를 남기며 이미 완료된 고객/입금 공유를 되돌리지 않습니다.

원본은 `earth/<workspaceId>/<graveId>/<versionId>/original.kml` 또는 `original.kmz`, 설명은 같은 폴더의 `manifest.json`입니다. manifest에는 회사/묘지/버전 ID·당시 주소·가져온 시각·파일명·크기·해시·geometry·대표 좌표·면적이 있습니다. `earth-staging/`는 성공 시 정리하며 중단된 전송 정리는 별도 만료 규칙을 사용할 수 있습니다. 원본 다운로드는 사장님/마스터만 가능하고 서명 URL은 5분 후 만료됩니다. URL을 자료 ID로 저장하지 않습니다.

SQLite 자동 백업은 버전/위치 표를 포함하지만 원본 바이트는 포함하지 않습니다. **DB와 `.demo-earth`를 함께 보관**해야 합니다. 서버 원본은 어스 자료 복구/이전에 쓰며 전체 고객·청구 DB 백업을 대신하지 않습니다. 최신 활성 버전은 고객 catalog/DB에 있습니다. 최신 원본 업로드 검증과 ready 저장이 완료되면 같은 묘지의 이전 R2 원본·manifest·staging을 정리합니다. 과거 버전 메타데이터는 폐기 상태로 보존하여 재업로드·다운로드를 막으며, 늦은 쓰기나 일시적 삭제 실패를 잡기 위해 다음 동기화에서 최대 100개씩 미정리/오래 확인하지 않은 폐기 버전을 다시 확인합니다. 원본 업로드가 실패하면 이전 R2 정상 원본은 유지됩니다. 여러 묘지가 연결된 고객도 묘지마다 최신 원본을 각각 유지합니다. 구형 자료는 원본이 없을 수 있으며 다시 가져오기 전에는 좌표·면적만 공유합니다. 위성사진을 새로 수집하거나 촬영하지 않습니다.

`earth-files.cjs`는 **구글 어스로 찾기**를 누르면 지정된 Google Earth 공용 폴더의 감시를 새로 시작합니다. 클릭 시점에 폴더 바로 아래 KML/KMZ의 파일 정보를 기준으로 기록하고, 이후 새로 생기거나 변경된 파일 중 파일시스템 변경 시각이 마지막인 파일(같으면 수정 시각 순)을 자동으로 읽습니다. 변경 없는 기존 파일은 무시하며, 여러 후보가 있어도 최신 파일을 가져옵니다. 다시 찾기를 누르면 기준과 세션을 새로 만들고 이전 세션의 늦은 결과를 무시합니다. 하위 폴더는 탐색하지 않고 symlink는 거부합니다. 파일 정보가 반복 검사에서 안정되고 읽기 전후 동일할 때 파싱합니다. 선택 파일 경로와 내용 해시로 같은 파일의 중복 이벤트를 막습니다. 렌더러에는 일회성 세션 ID와 표시용 경로를 주고, 폴더 열기/복사는 메인이 해당 세션에서 검증한 경로만 사용합니다. 기존 파일도 직접 선택할 수 있으며 그 경로는 렌더러에 공개하지 않습니다.

자동 폴더에서 감지한 한 위치는 UI가 현재 주소·고객을 검사한 뒤 기존 저장 API로 반영합니다. 기존 고객은 백업·충돌 검사 후 즉시 저장하고 갱신된 revision으로 다음 변경을 처리합니다. 신규 고객은 폼의 별도 선택값에 반영하고 등록 버튼을 누를 때만 DB에 씁니다. 같은 후보 파일의 재저장도 자동 반영합니다. 저장 도중 새 파일 결과가 도착하면 가장 최근 결과까지 순서대로 처리하고, 실패한 내용은 다시 읽기/저장으로 재시도할 수 있습니다. 직접 선택한 파일은 수동 적용을 유지합니다. 팝업 닫기·로그아웃·DB 전환·창 닫기·리로드에서 감시를 정리하며 새 팝업은 같은 폴더에서 기준 파일 정보를 새로 기록합니다. 기존 주소·날짜별 폴더와 고객 자료는 삭제하지 않습니다.

## 고객 DB 자동 백업과 복구 확인

고객 등록·상세/엑셀 수정·영업 확인 저장·발송 금액 반영은 쓰기 잠금 안에서 변경 전 SQLite 백업을 만듭니다. 백업의 무결성·외래키·고객/묘지/금액 테이블을 검사한 후에만 완료된 백업으로 저장합니다. 백업 생성이나 검사에 실패하면 고객 변경은 취소합니다.

고객 저장이 성공한 뒤 같은 DB의 일반 자동 백업을 **최근 30개**까지 보관합니다. 시스템 시각이 바뀌어도 방금 만든 백업은 반드시 남습니다. 일반 자동 백업은 `<DB파일명>.<생성시각>.<UUID>.db` 형식입니다. `before-*` 구조 변경 백업, 수동 백업, 다른 DB의 백업, 전체 이전 백업은 삭제하지 않습니다. 기존 백업의 손상이 발견되거나 정리가 실패하면 남은 백업을 보존하고 경고를 기록합니다. 정리 실패를 이미 완료된 고객 저장의 실패로 표시하지 않습니다.

현재 백업을 읽기 전용으로 점검하려면 다음 명령을 사용합니다. 실제 DB를 복원하거나 삭제하지 않으며, 손상 또는 백업 없음은 실패 종료 코드로 알립니다.

```sh
node scripts/check-customer-backups.cjs "고객 DB의 전체 경로"
```

복구 시에는 앱을 종료하고 현재 DB를 별도로 보관한 뒤, 원하는 백업을 **별도 임시 폴더에 먼저 복사**해 검증합니다. 정상임을 확인한 사본으로 고객 DB를 교체하고 회사 ID와 고객 기록을 확인합니다. SQLite의 WAL/SHM 파일이 남아 있다면 다른 시점의 DB와 섞지 말고 기존 DB와 함께 보존해야 합니다. 실행 중인 DB에 백업을 덮어쓰지 않습니다.

이 자동 백업의 범위는 고객·묘지·연도별 금액과 고객 DB 안의 회사 ID입니다. 청구·입금 이벤트(`.demo-mobile`), 작업 파일, 앱 내부 초안, 서버/R2 자료는 포함하지 않습니다. 전체 이전 백업 이후의 이 자료들을 주기적으로 묶어 백업하는 기능은 아직 없습니다. 같은 디스크의 백업은 기기 고장·분실에 대비한 외부 백업을 대신하지 않습니다.

## 고객 DB 구조 정리

앱 시작과 DB 선택은 먼저 **읽기 전용으로 회사 연결과 구조만 검사**합니다. 최신 DB도 고객·묘지·금액의 필수 항목을 확인하며, 누락된 구조는 연결을 거부합니다. 정상 최신 DB에는 변환 안내나 구조 변경 백업이 추가로 생기지 않습니다. 구형 DB는 파일 전체 경로와 변경 내용을 안내하고 **백업 후 변환**을 선택해야 변경합니다. 기본 선택과 Esc는 취소입니다. 시작 시 취소하면 그 실행에서는 DB를 연결하지 않고 저장된 경로는 보존합니다. 다른 DB 선택 중 취소하거나 변환에 실패하면 기존 연결과 경로를 유지합니다.

`src/desktop/customer/database-preparation.cjs`가 기존 회사 ID 저장과 구조 정리를 한 번의 검증된 백업·하나의 트랜잭션으로 처리합니다. `.demo-backups/<DB파일명>.before-database-conversion.<UUID>.db`는 변경 전 상태입니다. 임시 `.partial` 파일을 만든 뒤 무결성·외래키·고객/묘지/금액 테이블 검사를 통과해야 완료 백업으로 표시합니다. 검사 실패 시 변환하지 않고 미완료 파일을 정리합니다. 변환·연결 내용 검사·DB 위치 저장이 성공해야 변환을 확정합니다. 위치 설정은 임시 파일에서 완성한 뒤 교체하므로 쓰기/교체 실패 시 이전 설정을 유지합니다. 변환 중 실패하면 회사 ID·컬럼 정리·변환 이력을 함께 롤백하며, 설정 교체 후 확정 전에 실패하면 이전 설정도 복원합니다. 정상 백업은 복구를 위해 보존합니다. 위치 설정 복원 자체가 실패하면 복구가 필요하다는 오류를 표시합니다. 전원 장애·강제 종료까지 DB와 설정 파일을 하나의 저장 장치 트랜잭션으로 묶지는 않습니다. 중단 후에는 정상 백업과 DB 위치를 확인합니다. 이 구조 변경 백업은 일반 백업 30개 정리 대상이 아닙니다.

승인한 구형 구조 정리는 `source_sheet`, `area_detail`, `photo_note`, `has_photo`, `contract_note`, `request_timing`, `manager_id`, `prev_manager` 열과 과거 고객 담당자용 `staff` 표를 제거합니다. Supabase의 직원 로그인 계정은 변경하지 않습니다. 기존 회사 ID는 고객 DB의 `demo_workspace` 또는 이전 업무 DB의 정확한 연결 정보로 확인하며, 알 수 없는 DB에 로그인한 회사 ID를 새로 부여하지 않습니다. 확인 창이 열린 사이 파일·구조·회사 연결 또는 로그인/현재 연결이 바뀌면 재확인하도록 중단합니다.

고객·묘지 ID와 나머지 자료, 연도별 금액, 작업 보고·사진·좌표 연결은 유지합니다. 고객 지역은 별도 컬럼 없이 주소에서 계산하며 주소가 불충분하면 미분류로 표시합니다. 신규 입력과 고객 상세 수정에서도 지역을 따로 입력하지 않습니다. 변환 이력은 `demo_schema_migrations`에 남습니다. 알 수 없는 열·인덱스·트리거 또는 외래키 오류가 있으면 변환을 중단합니다.

삭제 전 값은 복구용 백업과 기존 원본 Excel/Numbers에 남습니다. 이 변환은 서버의 과거 동기화 이력이나 다른 기기의 오래된 사본까지 영구 파기하는 작업은 아닙니다. 최신 고객 자료는 앱의 기존 자동 공유 흐름으로 전달되며, 바뀐 모바일 화면은 앱 업데이트가 필요합니다.

## 삭제하면 안 되는 자료

- 원본 고객 DB, 업무용 Excel/Numbers 원본과 사본, 사진, 미동기화 기록.
- 좌표 출처를 확인하는 증거 자료와 외부 코드·경계 데이터의 라이선스.
- 휴대폰 앱을 삭제하거나 앱 데이터를 초기화하면 그 기기의 사진과 미동기화 기록이 사라집니다.

공유 사진은 [작업 보고·R2 저장소](work-reports.md) 설정 후 R2에, 보고 메타데이터는 Supabase에 저장합니다. 기존 로컬 문자 사진을 일괄 이전하지는 않습니다. 은행 입금 문자 처리는 [입금 문자 안내](bank-deposits.md)를 참고합니다. 최종 확인 문자는 자동 발송하지 않고 사장님·마스터가 검토 후 발송합니다.

## 최초 고객 Excel 변환 도구

`database/local/import_excel.py`는 최초 자료를 SQLite로 변환하는 도구입니다. 평소 신규 등록은 앱에서 합니다. Python 환경에 openpyxl을 설치한 후 우선 다음처럼 점검합니다.

```sh
python3 database/local/import_excel.py "입력.xlsx" --dry-run --mask --report /tmp/demo-import-check.txt
```

실제 변환 시에는 `--db`로 새 파일 경로를 명시합니다. 기존 운영 DB에 `--rebuild`를 쓰면 삭제 후 재생성되므로 정리/실행 과정에서는 사용하지 않습니다. 스키마와 ERD는 `database/local/`에 함께 있습니다.

## 재생성 가능한 파일

`node_modules`, `mobile/node_modules`, `mobile/dist`, Android build 폴더는 설치/빌드 명령으로 다시 만들 수 있습니다. 앱 전용 폴더의 IndexedDB·Local Storage에는 미전송 자료가 있을 수 있으므로 캐시처럼 일괄 삭제하지 않습니다.

## 개인정보 후속판의 보관 범위

일반 고객 전송은 공용 DTO와 서버의 동일 허용 목록을 통과한 업무 항목만 포함한다. 원본 엑셀 행/시트/로컬 경로와 임의 추가 컬럼은 전송하지 않는다. 원본 DB와 원본 해시는 유지하며 실제 전송 JSON의 해시를 따로 검증한다.

영구 삭제는 거래 증빙의 ID·원문·해시를 확인한 뒤 업무 자료를 제거한다. 청구 기준 금액과 실제 입금을 구분하고, 일반 요약에 삭제 고객의 원문 연락처·본문을 넣지 않는다. 원문은 실제 owner/master 세션의 명시적 증빙 조회에서만 열며 닫기·세대 변경·로그아웃 때 화면에서 지운다. 최소 상대 식별은 엄격한 은행 대조에만 사용한다. 기록별 법적 보존기간은 미확정이며 자동 파기는 제공하지 않는다.

기존 자동 백업 30개 규칙은 복구용 개수 제한이며 개인정보 보존기간이 아니다. 외부 백업·수동 내보내기·오프라인 기기의 사본은 이번 소스 작업으로 삭제 완료를 보장하지 않는다.

## R2 파일과 DB 기록

개인정보 보호 모드 회사의 사진·KML 파일 위치는 `demo_desktop.stored_objects`가 기준입니다(키, 종류, 보고·원본 버전, 묘지 번호). R2에만 있는 파일은 고아이고, DB에 있는데 R2에 없는 파일은 누락입니다. 저장소 점검(`demo_desktop.storage_checks`)은 마지막 점검의 개수만 보관합니다. 자세한 규칙은 `docs/work-reports.md`의 "저장소 구조와 자동 정리"를 따릅니다.

## 신규 등록 검토 요청함

관리자와 영업은 신규 고객을 바로 저장하지 못하고 "검토 요청"으로 보냅니다. 요청은 `demo_desktop.registration_requests`에만 쌓이며(요청 ID, 보낸 사람, 정리된 입력 내용, 상태 `pending`/`approved`/`rejected`, 예약 묘지 번호 칸), 승인 전에는 고객·묘지 표, 공유 목록, 휴대폰 자료 어디에도 나타나지 않습니다. 보내는 쪽에는 조회 함수가 없고 접수 함수 `demo_desktop_registration_request`만 있습니다. 같은 요청 ID로 같은 내용을 다시 보내면 한 건으로 처리하고, 응답은 처리 결과(반려 등)를 알려 주지 않습니다. 한 사람이 처리 대기 중으로 둘 수 있는 요청은 200건까지입니다. 이 표는 DB에 등록된 자료가 아니므로 서버 DB 백업에서 제외합니다(NAS 백업은 보류 중). 검토 화면과 승인은 4-3, 반려와 같은 경계 차단과 남은 파일 정리는 4-4·4-5, 파일 보관은 4-2에서 만들었습니다. 반려하면 상태가 `rejected`가 되고 입력 내용·요청자 이름·예약 번호가 지워집니다. 같은 경계(파일 이름만 다르거나 다시 저장한 것)는 다른 묘지 또는 다른 대기 요청에 이미 있으면 `demo_desktop.boundary_keys`로 막습니다(이 표도 서버 DB 백업에서 제외).

### 묘지 번호 예약과 묘지 코드

신규 등록을 준비하는 사람이 어스 위치를 가져오기 시작하면 서버가 묘지 번호를 하나 예약합니다(`demo_desktop.registration_reservations`, 초안 ID별 1건, 24시간 뒤 자동 만료, 한 사람 최대 20건, 번호는 다시 쓰지 않음). 화면에는 `데모-{번호}-{확인글자}` 형태의 묘지 코드가 표시되고 클립보드에 복사됩니다. 확인글자는 번호에서 계산하므로 손으로 고친 코드는 다른 묘지와 맞지 않습니다. 코드에는 이름·전화번호가 들어가지 않습니다. 신규 등록을 하는 모든 역할(마스터·사장님·부마스터·관리자·영업)이 같은 방식으로 "내려받기" 폴더와 Google Earth 폴더를 함께 지켜보며, 파일 이름에 이 코드가 들어 있는 KML만 읽습니다. 마스터·부마스터가 바로 등록하면 그 묘지는 예약한 번호로 만들어지고 예약은 사용 처리됩니다(어스 위치를 붙였으면 KML 준비 단계부터 같은 번호를 씁니다). 예약이 없거나 24시간이 지났으면 등록을 막고 위치를 다시 가져오라고 안내합니다(`code-expired`). 서버 없이 이 PC의 DB만 쓰는 회사는 번호를 예약할 곳이 없어 코드 없이 예전 방식으로 동작합니다. 고객 이름은 항상 직접 입력합니다. KML 파일 이름은 이름 칸에 들어가지 않습니다. 예약 함수는 `demo_desktop_registration_reserve`, 취소는 `demo_desktop_registration_release`입니다. 팝업이 열려 코드가 나오는 순간부터 폴더를 지켜보며, 코드가 든 파일은 팝업을 열기 전에 저장했어도 읽습니다. "폴더 열기" 버튼은 이 PC의 Google Earth 폴더(설치본은 `문서/Demo/Google Earth`, `npm run dev:live` 개발 화면은 `artifacts/dev-live/Google Earth`)를 엽니다.

신규 등록 화면의 입력은 디스크에 보관하지 않습니다(2026-10-25 결정). 등록 버튼을 누를 때만 서버로 보내며, 버튼을 누르기 전에 앱이 꺼지면 입력은 사라집니다. 요청 번호는 화면 메모리에만 있어서, 앱이 켜진 채 응답을 못 받으면 입력을 고치지 않고 다시 누르는 것으로 같은 요청을 확인하고(서버가 중복 생성을 막음), 입력을 고치거나 서버가 거절하면 새 요청이 됩니다. 앱을 처음 연결할 때 끝나지 않은 신규 등록의 요청 기록(`abandonRegistrations`)을 버려서 기기 자료 정리를 막거나 KML 원본을 계속 붙잡지 않게 하고, 시작할 때 Google Earth·내려받기 폴더에 남은 묘지 코드 이름의 KML(`데모-번호-글자`, 브라우저가 붙인 " (1)" 포함)을 지웁니다. 서버의 번호 예약과 준비 업로드는 24시간 뒤 스스로 정리됩니다. 고객 수정·작업·영업 화면의 저장은 예전처럼 이어서 확인합니다.

영업·관리자의 "거절" 버튼은 "거절 요청"으로, 같은 검토 요청함에 `registration_status = 'declined'`로 쌓입니다(승인 시 거절 목록에 등록하는 일은 4-3·4-4에서 만듭니다). "내용 지우기" 버튼은 입력 칸을 비우고, 이어서 묘지 코드 예약을 풀고, 이 등록을 위해 읽은 KML 저장본(내려받기·Google Earth 폴더)을 지웁니다. 마스터·부마스터가 등록을 마쳐 양식이 비워질 때도 같은 저장본을 지웁니다(원본은 앱 보관 폴더와 서버에 남음). 지우기 전에 파일 내용이 읽을 때와 같은지(SHA-256) 확인하므로 다른 파일은 건드리지 않으며, 로그아웃 때도 같은 정리를 합니다.
