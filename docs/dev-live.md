# 실시간 개발 화면 (`npm run dev:live`)

개발 중인 코드를 저장하는 즉시 PC 앱과 휴대폰 화면에서 확인하기 위한 환경이다. **운영 서버·운영 키·실제 고객 자료는 사용하지 않는다.**

## 실행

1. Docker Desktop을 연다.
2. 프로젝트 폴더에서 실행한다.

```sh
npm run dev:live
```

처음 실행은 Docker 이미지 다운로드 때문에 몇 분 걸린다. 준비가 끝나면 다음이 열린다.

- **PC 앱 창**: 제목과 화면 위에 `개발 화면 · 개발 서버 연결 (운영 아님)`이 표시된다.
- **휴대폰 화면**: Chrome에서 `http://127.0.0.1:56331`이 열린다.
- 터미널에 역할별 로그인 계정과 비밀번호가 출력된다. 직원 계정은 아이디만 입력한다.

## 코드가 바뀌면

| 바뀐 곳                                                       | 반영 방식                                                             |
| ------------------------------------------------------------- | --------------------------------------------------------------------- |
| `src/ui/` 화면 파일                                           | PC 앱 창이 자동 새로고침                                              |
| `src/desktop/`, `src/shared/`, `src/backend/` 등 앱 내부 코드 | PC 앱이 자동으로 다시 켜짐(로그인 유지)                               |
| `mobile/src/`                                                 | 휴대폰 화면 자동 빌드 후 Chrome 탭 새로고침                           |
| `database/cloud/**/*.sql`                                     | 개발 서버에 자동 적용. 실패하면 이전 상태 유지하고 터미널에 오류 표시 |
| `supabase/functions/`, `src/server/`                          | 서버 함수 다시 빌드                                                   |

## 개발 서버

- 별도 Docker 프로젝트 `demo-dev-live`(API `127.0.0.1:56321`, Studio `127.0.0.1:56323`)를 쓴다. `npm run local:start`의 로컬 테스트 서버(543xx)와 과천 테스트(553xx)와 섞이지 않는다.
- 처음에는 최신 운영 버전과 같은 구조를 설치하고, 그 위에 작업 중인 서버 SQL을 개발용 버전(`29991231-dev-…`)으로 적용한다. 보호 장치(스키마 지문 검사)는 그대로 켜져 있다.
- 샘플 회사: 가상 고객 20명(과천 주소, 이름 `샘플 고객01`~, 전화번호 없음), 그중 12명은 올해 진행 작업. 공동 모드·회계 보존 모드가 켜진 운영과 같은 상태다.
- **파일 저장소(R2 대신)**: 개발 화면은 운영 R2 대신 이 Mac 안의 개발용 저장소(`scripts/dev-live/storage.cjs`, `http://127.0.0.1:56390`)를 쓴다. 개발 서버 함수는 `host.docker.internal:56390`으로, PC 앱은 `127.0.0.1:56390`으로 접속하며, R2와 같은 서명 확인을 거친다. 파일은 `artifacts/dev-live/storage/demo-dev-live/` 아래에 R2와 같은 폴더 모양으로 저장되어 Finder에서 바로 볼 수 있고, 브라우저에서 `http://127.0.0.1:56390/`을 열면 파일 목록이 보인다. 저장소는 PC 앱 창이 열려 있는 동안만 켜진다. 처음 이 설정이 생기면 개발 서버를 한 번 다시 시작한다(자동).
- 터미널 진단 줄: `[앱 요청 실패] 요청: 이유` (화면에 짧은 안내만 보인 실패의 실제 이유), `[서버 함수] …` (서버 함수가 남긴 실패 이유), `[개발 저장소] 업로드 실패 …` (개발 저장소로 파일을 보내지 못함). 화면 파일(`src/ui/`) 변경은 창만 새로고침되고, 이 줄을 바꾸는 `scripts/dev-live/` 변경은 `npm run dev:live`를 다시 시작해야 적용된다.
- 개발 서버 함수는 자기 Supabase 입구(`supabase_kong_demo-dev-live`)를 이름으로 부른다(`DEMO_SUPABASE_INTERNAL_URL`). 로컬 테스트 도구들이 Docker 네트워크 하나를 같이 쓰기 때문에, 짧은 이름 `kong`이 다른 로컬 프로젝트로 연결되어 "User from sub claim in JWT does not exist"로 로그인 확인이 실패하는 일을 막는다. 운영에서는 이 값을 두지 않는다.
- PC 앱의 어스 KML 원본 보관·열기는 개발 저장소로 동작한다. 휴대폰 화면의 작업 사진 업로드와 PC의 작업 보고 사진 보기는 아직 운영 R2 주소만 받으므로 개발 화면에서는 실패한다(7단계에서 정리).
- 앱 창을 닫아도 서버는 켜져 있다. 끄기: `npm run dev:live:stop`. 자료는 보존된다.
- 자료와 앱 설정은 `artifacts/dev-live/`(Git 제외)에만 저장된다.
