# 회사 NAS 백업 (설계, 2026-10-28)

회사 NAS(QNAP TS-231P, 4TB)가 매일 새벽 서버 자료를 읽기만 해서 가져와 보관한다. NAS는 바깥으로 요청만 보내고,
외부에서 NAS로 들어오는 포트는 열지 않는다. 회사 PC·앱이 켜져 있을 필요는 없고 NAS만 켜져 있으면 된다.

## 대상과 방식

| 대상                                         | 방식                         | 보관                                            |
| -------------------------------------------- | ---------------------------- | ----------------------------------------------- |
| Supabase DB (업무 자료 + 로그인 계정 `auth`) | 매일 전체 덤프               | 최근 30일은 매일, 그 전은 매월 1일 것 12개월    |
| R2 정식 파일 (KML 원본, 스크린샷, 작업 사진) | 매일 새로 생기거나 바뀐 것만 | `현재`는 R2와 같게, 빠진 파일은 날짜 폴더에 1년 |

- R2의 `staging/`(등록 전 임시)와 `review/`(검토 요청) 파일은 넣지 않는다.
- R2에서 지워지거나 내용이 바뀐 파일은 지우지 않고 `변경·삭제/날짜/`로 옮긴다(같은 폴더 구조). 1년 지난 날짜 폴더는 지운다.
- 앱은 파일을 덮어쓰지 않고 새 이름으로 저장하므로, 파일 하나는 NAS에 한 번만 있다(현재 → 날짜 폴더로 이동).

```
demo-backup/
├─ DB/매일/2026-10-28.dump …   DB/매월/2026-10-01.dump …
├─ 파일/현재/{회사}/지역/시군/묘지/…
├─ 파일/변경·삭제/2026-10-28/…
└─ 마지막 성공.txt
```

## 실행

- NAS Container Station의 작은 컨테이너 하나: `pg_dump`(DB) + `rclone`(R2, 증분). 32비트 ARM에서 동작하는 이미지를 쓴다.
- 매일 새벽 3시(한국 시간). NAS가 그 시각에 꺼져 있었으면, 켜진 뒤 마지막 성공이 24시간을 넘었을 때 한 번 실행한다.
- 서버 계정은 읽기 전용: DB는 백업 전용 읽기 계정, R2는 버킷 읽기 전용 토큰. NAS가 털려도 서버 자료를 바꾸거나 지울 수 없다.
- 알림(QNAP 알림 메일): 실패했을 때, 하루에 바뀌거나 지워진 파일 양이 기준(예: 1GB)을 넘을 때.

## 사용량

- Supabase 무료 플랜 egress 월 5GB 중 DB 덤프(하루 수 MB)는 몇 %. 사진·스크린샷은 DB가 아니라 R2에 있다.
- R2는 내려받기 요금이 없고, 증분이라 새 파일만 한 번씩 받는다.

## 복구 (상황별 설명서·스크립트는 구현 단계에서 작성)

1. DB 일부 손상: 해당 날짜 덤프를 같은 Supabase 프로젝트에 복원(몇 분). 앱 재설치 불필요.
2. R2 파일 손실: `파일/현재`(필요하면 날짜 폴더)를 R2로 다시 올림.
3. 프로젝트 자체 손실: 새 프로젝트에 구조 → 자료 → 함수 순서로 복원, 주소가 바뀌므로 앱을 새로 만들어 설치.

- 마지막 백업 이후 입력분은 없다(최대 하루). 복원 뒤 모든 기기를 로그아웃·재로그인한다.
- 구현 마지막 단계에서 개발 화면(`npm run dev:live`)에 실제로 복원해 로그인·자료를 확인한다.

## 진행 단계

1. NAS 확인: Container Station, 공유 폴더 `demo-backup`
2. 파일 백업: R2 읽기 전용 토큰, 첫 전체 복사
3. DB 백업: 백업 전용 읽기 계정(SQL Editor), 첫 덤프
4. 자동화: 매일 실행, 오래된 것 정리, 알림
5. 복원 시험
