# 휴대폰 설치와 자동 공유

## 여러 데스크톱의 공동 원본

공유 모드에서는 서버의 고객·묘지·연도별 청구 금액·연간 작업·위치·Earth 연결이 원본입니다. PC의 SQLite는 권한을 확인한 회사의 조회 사본이며 전체 catalog/map을 게시하지 않습니다. 청구·실제 입금·작업 보고 이벤트는 기존 ID로 합쳐집니다. 직원용 소비 형식은 유지하고 삭제·거절 고객을 제외합니다.

최종 등록·수정·삭제는 온라인에서만 합니다. 끊긴 연결에서는 마지막 받은 시각과 자료를 조회하고 입력 초안을 보관합니다. 결과가 불명확하면 같은 요청 번호를 확인·재시도합니다. 이미 저장된 입력과 새로 작성한 입력은 별도 요청이며, 이전 결과 확인 뒤 새 입력을 검토하고 다시 저장합니다. 다른 사람이 먼저 수정했으면 최신 값과 입력을 비교하고 명시적으로 버전을 갱신한 뒤 저장합니다.

영업 확인은 서버에서 해당 창에 배정된 고객만 표시합니다. 15초마다 확인하며 확인 실패·절전·화면 잠금에는 전화번호 표시와 입력/저장을 잠급니다. 90초 확인이 없는 배정은 확인 필요 상태로 계속 점유됩니다. 강제 종료·로그아웃은 자동 해제가 아닙니다. 이동/닫기/저장은 통화 종료와 미저장 입력을 확인합니다. 확인 필요 목록의 담당자·시각을 보고 자기 초안을 재개하거나, 통화가 끝난 것을 확인하고 사유를 남겨 해제합니다.

Supabase와 R2를 그대로 쓰며 별도 서버는 추가하지 않습니다.

## 서버와 앱 업데이트

서버 SQL은 [SQL 적용과 검증](sql-application.md)의 버전 절차를 따릅니다. 기존 회사에 초기화나 기능별 과거 SQL을 다시 실행하지 않습니다. 새 빈 서버 설치에는 자동 공유·완료 문자 규칙이 포함됩니다.

완료 문자 결과 검증은 공통 원본과 보호 대상 이벤트 제약으로 관리합니다. SQL 정의 변경은 승인된 버전 트랜잭션으로 적용하고 verify로 확인합니다. 이 SQL 변경만으로 Edge Function이나 설치된 앱이 업데이트되지는 않습니다.

SQL 적용 후 데스크톱을 다시 실행하고 Android·iPhone 앱을 새 빌드로 업데이트합니다. 앱을 삭제하지 않아야 미전송 기록과 로컬 사진이 유지됩니다. 실제 서버 적용 여부와 기기 설치 여부는 작업 완료 안내를 따릅니다. 소스 변경만으로 설치된 앱이 업데이트되지는 않습니다.

새 회사 연결은 [계정 안내](access.md)의 최초 설정과 [지도 안내](maps.md)를 따릅니다. 앱에 포함하는 것은 공개 프로젝트 연결 정보이며 비밀 키나 계정 비밀번호가 아닙니다.

## 자동으로 공유되는 자료

| 자료                             | 전달 방식                                                      |
| -------------------------------- | -------------------------------------------------------------- |
| 고객·묘지·작업 조회 자료         | 회사 PC 저장 후 자동 게시, 역할별 조회                         |
| 지도 좌표                        | PC에 저장된 유효한 좌표 공유, 휴대폰에서 주소 재조회하지 않음  |
| 작업 보고                        | 사진 업로드와 등록이 완료된 뒤 회사 전체의 열린 목록 자동 갱신 |
| 청구서(문자 발송·입금·최종 문자) | 서버에만 보관, 바뀌면 청구 신호로 PC·휴대폰 목록 갱신          |
| 작업 보고 사진                   | 보고를 선택할 때 R2에서 조회                                   |

앱 실행·복귀·인터넷 재연결 때 변경 여부를 확인합니다. 사용 중에는 작은 변경 알림을 받아 필요한 자료를 조회하며 주기적으로 전체 DB를 내려받지 않습니다. 사장님·마스터는 기존 변경 순번을 사용합니다. 직원은 변경이 있을 때 허용된 자료 묶음을 받습니다. 직원 자료는 실행 세션 메모리에 있어 앱을 완전히 다시 실행하면 다시 받아야 합니다.

회사 PC가 꺼져 있어도 작업 보고 등록·조회와 휴대폰 간 청구·입금 공유는 가능합니다. PC의 고객 원본에 문자 발송 금액을 반영하는 일은 다음 PC 실행 때 처리합니다. 휴대폰은 만료된 지도 좌표를 계속 사용하지 않습니다.

인터넷 오류는 기록을 지우지 않고 사용 중에 제한적으로 재시도합니다. 이후에는 앱 복귀·재연결·설정의 **최신 자료 다시 불러오기**으로 다시 처리합니다. 사진 등록 실패는 초안을 유지하며 **등록**을 다시 눌러야 합니다. 동기화 재시도가 문자를 다시 보내지는 않습니다.

설정의 **최신 자료 다시 불러오기**은 수동 복구 경로입니다. 평소 저장 후 별도 버튼을 누를 필요가 없습니다. 일반 화면과 직원 계정 관리에는 수동 동기화 버튼을 표시하지 않습니다. 기기의 로그인 유지 통신·실시간 알림·사진 조회는 서비스 사용량에 포함되므로 무료 사용량을 보장하지 않습니다.

## 설치와 빌드

PC 실행, 휴대폰 화면 미리보기, 갤럭시 APK·iPhone 빌드와 설치 명령은 [개발 안내](development.md)에만 둡니다. 휴대폰 앱에는 회사 연결이 들어 있으므로 발급받은 아이디 또는 이메일과 비밀번호만 입력하면 됩니다.

## 실제 업무 흐름 (2026-10-26부터)

청구서는 서버에만 있습니다. 한 묘지에 한 해 하나이며, 작업자가 배정 작업의 사진 보고를 올리면 생깁니다.
사장님·마스터·부마스터 휴대폰은 같은 앱입니다(메뉴: 고객 찾기 · 작업 현황 · 작업 확인 · 청구 · 설정).

1. **작업 확인**: 청구 문자를 아직 안 보낸 청구서가 최근 보고 순으로 나옵니다. 누르면 청구 문자 화면이 열립니다.
   보고 사진(최대 10장)을 고르고 금액을 확인·수정한 뒤 **확인 · 발송**을 누르면 갤럭시 유심으로 SMS/MMS를 보냅니다.
   금액을 고치면 그 묘지의 올해 금액도 같이 바뀝니다. 다른 휴대폰이 보내는 중인 청구서는 10분 동안 흐리게 잠깁니다.
   휴대폰이 결과를 확인하지 못하면 **보냈어요**(문자 앱에서 확인한 뒤) 또는 **다시 보내기**를 고릅니다.
2. **청구 → 입금 대기**: 청구 문자를 보낸 청구서입니다. 갤럭시 입금 문자가 이름·금액이 딱 맞는 청구서 하나를 찾으면
   자동으로 입금 확인되고([은행 문자 자동 처리](bank-deposits.md)), 나머지는 PC 청구·입금 화면의 **확인 대기**에서 사람이 고릅니다.
   휴대폰에서 직접 받은 날·입금자를 넣고 **입금 확인**할 수도 있습니다.
3. **청구 → 최종 문자**: 입금된 청구서입니다. **최종 문자 보내기**로 아래 감사 문자를 보내면 끝납니다.
   문자 전에 입금된 청구서는 작업 확인을 건너뛰고 바로 여기에 나옵니다.

문자는 갤럭시에서만 보냅니다. 갤러리 원본은 지우지 않으며, 보고 사진은 R2에서 받은 사본을 첨부합니다.

최종 확인 문구는 다음 세 줄을 사용합니다.

```text
감사합니다~
풍성한 한가위처럼 가정에 건강과 행복이 가득하시고,
사랑하는 가족들과 따뜻하고 풍요로운 추석 명절 보내시길 바랍니다^^
```

### 기기 권한

- 문자 발송 권한만 요청합니다. 미디어 관리·삭제 권한은 요청하지 않습니다.
- 사진 문자는 최대 10장·합계 20MB이며 발송 시 통신사 제한에 맞춰 압축합니다. 듀얼 SIM은 Android 설정에서 기본 문자 SIM을 지정해야 합니다.
- 휴대폰 요금제의 SMS/MMS 조건이 적용됩니다. 별도 문자 발송 업체 API는 쓰지 않습니다.

## 저장되는 곳

- 앱 전용 폴더의 `data/company.db` ([저장 위치](data.md)): 기존 고객 관리 기능이 사용합니다. 문자 발송 금액을 기존 매칭 규칙으로 고객의 올해 금액에 반영하고 다시 게시합니다.
- 고객 DB의 `demo_workspace`: 고정 회사 ID를 보관합니다. 최초 실행 시 기존 `.demo-mobile/field.db`의 해당 파일명에 연결된 ID를 그대로 옮기며, 이후 파일명이나 경로로 ID를 만들지 않습니다. 변경 전 `.demo-backups`에 복구용 DB를 만들고 `demo_schema_migrations`에 적용을 기록합니다. 기존 로그인 회사와 다른 ID이거나 ID를 확인할 수 없는 DB를 선택하면 연결 교체를 거절합니다. 이미 잘못 이름을 바꾼 구버전 DB는 원래 이름과 `.demo-mobile`을 복원한 뒤 변환해야 합니다.
- DB 옆 `.demo-mobile/field.db`: 청구·입금·연결 이력, 동기화 진행 상태, 공개 연결 설정을 보관합니다. 기존 파일명 기반 ID 항목은 복구를 위해 남기지만 변환 이후에는 사용하지 않습니다. DB만 복사해도 회사 ID는 유지되지만 미전송 기록·설정·작업 자료까지 옮겨지지는 않습니다. 다른 회사 노트북으로 옮길 때 고객 DB, `작업자료`, `.demo-mobile`, 지도 관련 폴더를 함께 옮깁니다. 같은 DB 사본을 여러 PC에서 동시에 수정·게시하는 용도로 쓰지 않습니다.
- 휴대폰 앱의 로컬 저장소: 내려받은 고객·작업 자료, 작업 보고 초안, 이 휴대폰이 보낸 문자의 전송 기록(결과를 서버에 남기기 전까지). Android의 전송 대기·결과는 앱 전용 파일에 별도로 기록하여 화면 종료 후에도 복구합니다. 청구서는 서버에만 있습니다.
- Supabase: 고객·작업 자료, 청구·입금·연결 이력, 변경분 전달용 순번과 변경 기록을 저장합니다. 사진 파일 대신 작업 보고 메타데이터도 저장합니다. 데이터는 동기화 완료 후에도 남으며, 변경 기록도 DB 저장 용량에 포함됩니다.
- 데스크톱은 로그인 토큰을 메모리에만 유지하여 앱 재실행 시 로그인합니다. Android는 암호화 저장소, iPhone은 Keychain에 로그인 토큰을 보관하여 로그아웃 전까지 세션을 복원하며 비밀번호는 저장하지 않습니다. 로그인 후 필요한 자료를 자동으로 받습니다. 휴대폰 앱이 꺼진 동안의 백그라운드 동기화는 없으며 다시 열 때 따라잡습니다.

## 검증 상태

`npm test`로 검색, 중복 후보, 이벤트 병합, 변경 없는 동기화, 행 수정·삭제, 오프라인 기록 수신, 재시도, 서버의 작은 페이지 제한, 기존 클라우드 자료의 전환, 동기화 중 동시 저장, 자동 변경 알림·게시와 발송·입금·취소·삭제의 중복 없는 자동 업로드, 수동 재시도, 사진 로딩 중 고객 변경, 청구·입금 계산, 갤러리 원본을 삭제하지 않는 전송 결과 처리, 기존 DB 보존과 로컬 PostgreSQL의 계정별 접근 제한을 검사합니다. Android 테스트에서는 전송 결과 영구 저장, 중복 콜백, 중단된 저장 복구, 일부 실패, 지연 성공과 MMS 한글·이미지 구성 및 크기 제한을 확인합니다. 실제 Supabase 프로젝트와 휴대폰이 연결되기 전에는 온라인 연동·실제 SMS/MMS 발송을 보장하는 테스트로 볼 수 없습니다.

## 사진 공유와 직원 계정

직원별 계정과 역할은 [계정 관리](access.md)를 따릅니다. 작업 보고·R2 사진 공유는 [사진 저장소](work-reports.md)의 서버 설정 후 사용합니다. 일반 작업자가 배정 작업에서 올리고 회사 전체가 조회합니다. 보고는 등록 완료 즉시 공유되고 모든 활성 직원 계정의 열린 작업 보고 목록을 자동 갱신합니다. 사장님·마스터는 별도 billing 신호로 청구·입금 변경분도 받습니다. 사진은 보고를 선택할 때만 가져옵니다. 무료 한도나 예상 가격은 기능 보장에 포함하지 않습니다.

배포 APK의 버전과 재빌드 방법은 [개발 안내](development.md)를 확인하세요.

## 청구·입금 기록 삭제

기록 상세의 **청구·입금 기록 삭제**를 누르고 확인하면 해당 청구와 연결된 입금 내역이 목록에서 사라집니다. 고객 DB와 작업 보고 사진, 이미 발송한 문자는 변경하지 않습니다. 삭제 이력(`claim_deleted`)을 보관해 오래된 기기와 병합해도 청구가 다시 나타나지 않습니다. 청구 삭제 이력은 온라인이면 자동 전송하고, 오프라인이면 앱 실행·재접속 시 다시 전송합니다.

청구 삭제·완료 문자 이벤트는 현재 공통 이벤트 제약에 함께 포함됩니다. 기존 서버의 규칙 변경은 [SQL 적용과 검증](sql-application.md)을 따릅니다. 휴대폰은 최신 APK로 업데이트한 후 동기화해야 새 이력을 읽을 수 있습니다.

복구용 버튼은 휴대폰 화면의 **설정 → 자료 관리 → 최신 자료 다시 불러오기**에만 있습니다. 직원도 설정에서 동기화와 로그아웃을 사용할 수 있으며 청구·입금과 사장님 전용 설정 권한은 부여하지 않습니다.

### 변경 없는 동기화 생략

조건부 동기화는 현재 설치 버전에 포함됩니다. 기존 서버는 통합 버전 절차로 업데이트하며 기존 직원 조회 API를 유지합니다.

사장님 기록은 변경 순번과 미전송 기록을 확인하고 변화가 없으면 본문 전송·저장을 생략합니다. 지도는 회사·계정별 마지막 수신 버전과 로컬 자료가 모두 일치할 때 작은 확인 응답만 받습니다. 데스크톱에서 지도가 바뀌면 해당 스냅샷만 전송합니다. 직원 자료는 현재 계정에 허용된 고객·작업·유효한 좌표의 버전으로 비교하므로, 전화번호 변경이나 좌표 만료도 놓치지 않습니다. 권한은 매번 확인하며 사용 중지된 직원은 최신 버전을 가지고 있어도 거절합니다.

버튼을 누를 때 변경 확인 통신은 남습니다. 처음 연결하거나 앱에서 로컬 자료가 사라진 경우에는 자료를 받아야 합니다. 직원 자료는 메모리에만 보관하므로 앱 재시작 후에는 처음 동기화에서 다시 받습니다. 모든 계정은 자동 변경 알림과 실행·복귀 시 확인을 사용합니다. 설정의 버튼은 재확인 용도입니다. 직원 자료도 [자동 공유](access.md#직원-자료-자동-공유)를 사용하며 백그라운드 강제 실행은 없습니다.

## 개인정보 처리 세대

전환된 회사는 raw 이벤트/과거 전체 자료 경로 대신 업무 snapshot과 제한된 FinancialView를 받는다. 이전 로컬 기록은 같은 이벤트/요청 ID와 원문 해시로 확인한 뒤 교체한다. 미확인 거래는 격리해 보존하며 자동 재전송하지 않는다. 직원은 기존 직원용 catalog/map과 삭제 메타데이터만 사용하고 회계 reconcile/원문 API를 호출하지 않는다.

기기 정리 확인은 저장소 교체·초안/관리 사본 정리가 끝난 뒤에만 전송한다. 정리 중 이전 초안 저장이 되살아나지 않도록 대기열에서 세대를 재확인한다. 작업 연결은 고객/묘지 ID만 가진 별도 업무 항목으로 유지한다. 구버전·미접속 기기는 업데이트/다음 온라인 확인이 필요하다.
