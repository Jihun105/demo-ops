# Docker로 데모 로컬 서버 배우기

이 환경은 맥 안에서 가짜 회사·고객·입금 자료로 서버 기능을 연습하는 곳입니다. Docker가 서버들을 실행하고, Supabase CLI가 그 서버들을 함께 준비합니다. 회사에서 쓰는 Supabase와 R2 연결, 데스크톱 프로그램, 직원 휴대폰의 설정은 바꾸지 않습니다.

먼저 아래 순서로 시작한 뒤, 실행 중인 서버를 보면서 Docker의 네 가지 개념을 익히면 됩니다. 이 안내는 맥을 기준으로 작성했습니다. Windows에서의 실제 실행은 아직 별도로 검증하지 않았습니다.

## 1. 처음 한 번 준비하기

프로젝트 폴더에서 터미널을 열어 아래 명령을 실행합니다. Node.js는 프로젝트에서 요구하는 24 이상을 사용합니다.

```sh
npm ci
```

`npm ci`는 잠금 파일에 기록된 버전으로 필요한 프로그램을 설치합니다. 이 프로젝트에는 Supabase CLI `2.120.0`이 개발용 의존성으로 들어 있으므로 CLI를 따로 설치할 필요는 없습니다. 처음 설치할 때는 인터넷이 필요합니다.

이어서 Docker Desktop을 열고 실행 준비가 끝날 때까지 기다립니다. 이 맥에서는 `/Applications/AI/Docker.app`에 설치되어 있습니다. Docker Desktop은 맥 안에서 컨테이너를 실행할 수 있게 해 주는 프로그램입니다.

## 2. 서버를 시작하고 확인하기

Docker Desktop이 실행 중인 상태에서 순서대로 실행합니다.

```sh
npm run local:start
npm run local:status
npm run local:test
```

- `local:start`: DB·로그인·API·실시간 알림·Studio·은행 입금 함수를 시작하고 가짜 자료를 준비합니다.
- `local:status`: `demo-local-test` 프로젝트의 주소와 컨테이너 실행 상태를 보여 줍니다.
- `local:test`: 실제 로컬 로그인과 HTTP 요청으로 권한·입금 판정·중복 방지·실시간 알림을 검사합니다. 실행 결과를 보고 성공 여부를 확인합니다.

첫 시작은 Supabase가 사용하는 이미지들을 다운로드하므로 시간이 걸릴 수 있습니다. 이후에는 저장된 이미지를 재사용합니다. 로컬 검증은 운영 Supabase나 R2의 사용량을 소비하지 않으며, 맥의 메모리와 디스크를 사용합니다. [Supabase 로컬 개발 안내](https://supabase.com/docs/guides/local-development)

서버가 준비되면 브라우저에서 [로컬 Studio](http://127.0.0.1:54323)를 엽니다. Studio는 가짜 DB 자료를 볼 수 있는 관리 화면입니다.

| 주소·포트                | 역할                                      | 사용하는 방법                                |
| ------------------------ | ----------------------------------------- | -------------------------------------------- |
| `http://127.0.0.1:54321` | 로그인·자료 요청·입금 함수가 들어오는 API | 테스트 도구가 사용합니다.                    |
| `127.0.0.1:54322`        | PostgreSQL DB                             | DB 도구의 연결 주소이며 웹페이지가 아닙니다. |
| `http://127.0.0.1:54323` | Studio                                    | 브라우저로 가짜 자료를 봅니다.               |

`127.0.0.1`은 지금 사용하는 맥 자신을 가리킵니다. 별도 Docker 네트워크 `demo-local-test-loopback`을 사용하며, 게시 포트는 `127.0.0.1`과 같은 로컬 주소인 IPv6 `::1`만 허용합니다. 다른 PC나 휴대폰에서 접속하는 주소가 아닙니다. 명령은 원격 Docker 연결도 거절합니다. [Supabase의 로컬 네트워크 설정](https://supabase.com/docs/guides/local-development)

Docker Desktop에서는 네트워크 옵션만으로 제한이 적용되지 않을 수 있습니다. **Settings → Resources → Network → Port binding behavior → Localhost by default**를 선택합니다. 이 맥에는 그 설정을 적용했고, 기존 설정 사본은 Git 제외 경로 `artifacts/local-test/docker-settings-before.json`에 보관했습니다. 이 설정은 새 컨테이너의 기본 연결 주소에도 적용됩니다. 다른 프로젝트를 외부 기기에서 접속해야 한다면 해당 프로젝트의 포트 주소를 명시적으로 지정하세요. 도구는 바인딩이 외부 주소로 열리면 데모 테스트 프로젝트만 중지하고 실패를 알려줍니다. [Docker 포트 설정](https://docs.docker.com/desktop/enterprise/hardened-desktop/settings-management/settings-reference/)

## 3. Docker의 네 가지 개념을 실제 서버에서 보기

### 이미지: 서버를 실행하는 데 필요한 묶음

이미지는 프로그램과 실행에 필요한 파일·라이브러리·설정을 담은 묶음입니다. 이번에는 DB, 로그인, Studio 등을 위한 Supabase의 이미지를 내려받습니다. 이미지를 받았다고 서버가 계속 실행되는 것은 아닙니다. [Docker 이미지 설명](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-an-image/)

Docker Desktop의 **Images** 화면이나 아래 명령으로 맥에 저장된 이미지를 볼 수 있습니다. 기존 다른 프로젝트의 이미지도 목록에 보일 수 있습니다.

```sh
docker image ls
```

이번 환경은 Supabase CLI가 기존 이미지를 조합하므로 새 Dockerfile을 만들거나 서버 프로그램들을 맥에 하나씩 설치하지 않습니다.

### 컨테이너: 이미지로 실행한 서버

컨테이너는 이미지에서 실제로 실행한 프로그램의 독립된 실행 공간입니다. 하나의 회사 기능을 위해 여러 컨테이너가 협력합니다. DB는 자료를 저장하고, Auth는 로그인 정보를 확인하고, API는 요청을 받아 DB에 연결하고, Realtime은 변경을 알려 줍니다. Edge Runtime은 은행 입금 함수를 실행하고, Studio는 DB 관리 화면을 제공합니다. [Docker 컨테이너 설명](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/)

Docker Desktop의 **Containers** 화면에서 이름에 `demo-local-test`가 들어간 서버들을 봅니다. 터미널에서는 이 프로젝트만 골라 볼 수 있습니다.

```sh
docker ps -a --filter label=com.supabase.cli.project=demo-local-test --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
```

`local:start` 후 여러 서버가 실행 중이어도 여러 회사 서버를 만든 것은 아닙니다. DB·로그인·함수 등 역할별 서버들이 한 로컬 프로젝트 안에서 함께 작동하는 것입니다.

### 포트: 맥에서 컨테이너로 들어가는 통로

컨테이너 안의 서버와 맥의 브라우저는 별개의 실행 공간에 있습니다. 포트 연결이 둘 사이의 통로를 만듭니다. 브라우저가 `127.0.0.1:54323`을 열면 Studio 컨테이너의 웹서버로 요청이 전달됩니다. 같은 맥에서도 API는 `54321`, Studio는 `54323`으로 구분합니다. [Docker 포트 설명](https://docs.docker.com/get-started/docker-concepts/running-containers/publishing-ports/)

위 컨테이너 목록의 `Ports` 열에서 `127.0.0.1`로 시작하는 연결을 확인해 보세요. 주소가 같은 맥을 가리키고, 번호가 들어갈 서비스를 구분합니다.

### 볼륨: 서버를 꺼도 자료가 남는 저장 공간

볼륨은 Docker가 관리하는 저장 공간입니다. 이 환경은 로컬 DB 자료를 보존하므로 서버를 정지한 뒤 다시 시작해도 가짜 자료를 이어서 사용할 수 있습니다. [Docker 볼륨 설명](https://docs.docker.com/engine/storage/volumes/)

Docker Desktop의 **Volumes** 화면이나 아래 명령으로 이 프로젝트 이름이 포함된 볼륨을 봅니다.

```sh
docker volume ls --filter name=demo-local-test
```

볼륨은 맥 안에 자료를 유지하는 기능입니다. 별도 기기나 외부 저장소에 보관한 백업은 아니므로 맥이나 Docker 저장 공간을 잃었을 때의 복구 수단과 구분해야 합니다.

## 4. 가짜 계정과 자료 살펴보기

최초 준비되는 계정은 아래와 같습니다. 모두 연습용 이메일이며 비밀번호는 `Demo-local-test-123!`입니다.

| 역할             | 이메일                          | 연습 목적                               |
| ---------------- | ------------------------------- | --------------------------------------- |
| 사장님           | `owner@demo.local.invalid`      | 가짜 회사의 자료·금융 기능 접근         |
| 마스터           | `master@demo.local.invalid`     | 같은 회사의 관리·금융 기능 접근         |
| 관리자           | `manager@demo.local.invalid`    | 금융 자료 접근이 차단되는지 확인        |
| 일반 작업자      | `worker@demo.local.invalid`     | 금융 자료 접근이 차단되는지 확인        |
| 다른 회사 사장님 | `otherowner@demo.local.invalid` | 회사 사이의 자료 접근이 차단되는지 확인 |

이 계정은 로컬 Auth 관리자 API로 이메일 확인이 끝난 상태로 만들어집니다. 회원가입이나 확인 메일 수신 과정이 필요하지 않습니다. 가짜 고객은 `로컬 가상고객`, 번호는 `01000000000`, 주소는 `로컬 테스트 구역 1`이며 80,000원 청구와 가짜 문자 발송 성공 기록이 준비됩니다. 발송 성공 기록은 DB의 테스트 자료이며 실제 문자나 이메일을 보내지 않습니다.

Studio의 **Authentication → Users**에서 가짜 계정을 보고, **Table Editor**에서 `public` 스키마의 다음 표들을 살펴봅니다. 메뉴 표기는 Studio 버전에 따라 조금 다를 수 있습니다.

| 표                   | 살펴볼 내용                                                                                                                                           |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| `demo_catalogs`      | `payload` JSON 안의 `customers`와 `workRows`. 고객마다 표의 행이 하나씩 있는 구조가 아니라 회사 자료가 JSON으로 담겨 있습니다.                        |
| `demo_events`        | `claim_created`는 청구 생성, `dispatch_result`는 가짜 발송 결과, `payment_recorded`는 입금 반영 기록입니다. 금액과 청구 연결은 `payload`에서 봅니다.  |
| `demo_bank_receipts` | 입금 접수 자료. `status`의 `matched`는 연결 완료, `held`는 보류이고 `reason`에서 이유를 봅니다. 최초 가짜 회사에는 접수가 없어 비어 있을 수 있습니다. |
| `demo_sync_signals`  | `kind`가 `billing`인 행의 `revision`과 `updated_at`. 청구·입금 변경을 다른 연결에 알리기 위한 신호입니다.                                             |

`local:test`는 실행마다 별도의 임시 가짜 회사와 계정을 만들어 검사하고, 끝나면 그 회사의 계정·접수·이벤트를 정리합니다. 따라서 검사를 마쳐도 최초 가짜 회사의 80,000원 청구는 그대로이고, 입금 접수 표가 비어 있어도 정상입니다. 입금 판정은 아래 검증 결과에서 확인합니다. Studio는 DB를 관리하는 화면이므로, 사장님·작업자 계정의 앱 권한 차이는 `local:test`의 로그인 검사로 확인합니다.

이번 단계는 테스트 도구가 기존 SDK와 업무 연결 코드를 통해 로컬 서버에 직접 요청하는 방식입니다. 현재 데스크톱·휴대폰 앱을 로컬로 연결하는 UI 설정은 아직 없습니다. 앱의 회사 주소 칸에 `http://127.0.0.1:54321`을 넣으면 기존 주소 검증과 맞지 않으므로, 이 연습에서는 위 명령과 Studio를 사용합니다.

## 5. 업무 검증에서 무엇을 배우는가

```sh
npm run local:test
```

이 명령은 다음 경계를 실제 로컬 서비스로 검사합니다.

1. 가짜 이메일·비밀번호 로그인은 성공하고 잘못된 비밀번호는 거절되는지.
2. 사장님과 마스터는 같은 회사 금융 자료에 접근하고, 관리자·작업자·다른 회사 계정은 거절되는지.
3. 등록된 가짜 수신 기기의 입금 내용이 이름과 남은 금액이 유일하게 맞는 청구에 연결되는지.
4. 같은 입금을 다시 보내도 두 번 반영하지 않고, 금액 불일치나 후보가 여러 개인 경우는 보류하는지.
5. 미등록·해제된 가짜 기기의 요청은 거절되는지.
6. 다른 로그인 연결에 청구·입금 변경 알림이 도착하고, 바뀐 자료를 다시 조회할 수 있는지.

모든 검사가 끝나면 각 항목의 `status`와 함께 아래 요약을 출력합니다. 아래 값은 성공할 때 기대하는 결과이며, 실제 성공 여부는 본인의 명령 실행 결과로 확인합니다.

| 결과 항목       | 기대 값 | 뜻                                         |
| --------------- | ------- | ------------------------------------------ |
| `passed`        | `12`    | 로그인·권한·입금·알림 등 12개 검사 완료    |
| `matchedAmount` | `80000` | 가짜 청구에 반영된 입금 금액               |
| `paymentCount`  | `1`     | 재전송 이후에도 입금 반영은 한 번          |
| `heldReceipts`  | `3`     | 중복 내용·금액 불일치·동명이인 접수는 보류 |

실제 은행 문자 수신을 대신해 가짜 요청 데이터를 함수에 보냅니다. 따라서 이 검사로 직원 휴대폰의 문자 권한·백그라운드 수신·재설치까지 확인할 수는 없습니다. 사진 업로드와 R2, 지도 API, 실제 SMS 발송·수신도 이번 검증 범위에 포함되지 않습니다.

기존 `npm test`는 코드와 DB 규칙을 검사하는 자동 테스트입니다. `local:test`는 Docker 서버가 실행 중일 때 로그인·HTTP·Realtime·함수를 함께 확인하는 검사입니다.

`npm run test:integration`은 `npm run local:start`로 서버를 켠 뒤 실행하며, `tests/integration`의 실제 PostgreSQL 별도 세션 잠금·대기 테스트를 한 파일씩 실행합니다.

## 6. 정지·재시작·가짜 자료 준비·초기화

평소에는 아래 두 명령으로 껐다 켭니다.

```sh
npm run local:stop
npm run local:start
```

`local:stop`은 이 프로젝트의 서버를 정지하고 가짜 DB 자료를 보존합니다. 다음 `local:start`는 기존 자료를 이어서 사용합니다. 시작 명령은 최초 자료를 준비할 뿐, 이미 수정한 가짜 고객을 매번 처음 상태로 덮어쓰지 않습니다.

가짜 계정과 최초 자료를 준비하는 단계만 다시 실행하려면 서버가 켜진 상태에서 아래 명령을 사용합니다.

```sh
npm run local:seed
```

`seed`는 기존 가짜 자료를 유지하는 준비 명령입니다. 이전 입금 기록이나 직접 수정한 자료를 지우고 처음으로 되돌리는 명령은 아닙니다.

**연습 DB 전체를 처음으로 되돌릴 때만** 서버가 켜진 상태에서 실행합니다.

```sh
npm run local:reset
npm run local:test
```

`local:reset`은 `demo-local-test`의 로컬 DB를 지우고 SQL과 가짜 계정·고객·청구를 다시 준비합니다. Studio에서 직접 넣은 가짜 자료와 테스트 실행 기록도 삭제됩니다. 운영 DB나 다른 프로젝트를 초기화하는 명령은 제공하지 않습니다.

Docker Desktop에서 컨테이너나 볼륨을 직접 삭제하지 않아도 이 명령들로 반복 연습할 수 있습니다.

## 7. 시작할 때 문제가 생기면

| 증상                                           | 확인할 내용                                                                                                                                                                                                         |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `supabase`나 모듈을 찾지 못함                  | 프로젝트 폴더인지 확인하고 `npm ci`를 실행합니다.                                                                                                                                                                   |
| Docker 서버에 연결할 수 없음                   | Docker Desktop을 열고 준비가 끝났는지 확인합니다. `docker version`에 Client와 Server가 모두 표시되는지도 봅니다.                                                                                                    |
| 먼저 `local:start`를 실행하라는 안내           | `npm run local:start`를 실행한 뒤 상태·테스트·자료 준비 명령을 사용합니다.                                                                                                                                          |
| 포트가 사용 중이라는 안내                      | Docker Desktop과 본인이 실행한 앱에서 54321·54322·54323 사용 여부를 확인합니다. 다른 프로젝트가 사용 중이면 해당 프로젝트의 절차로 정지하거나 충돌을 먼저 해결합니다. 이 도구는 다른 앱을 강제로 종료하지 않습니다. |
| 원격 Docker를 사용할 수 없다는 안내            | `docker context ls`에서 Docker Desktop의 로컬 context를 확인합니다. 원격 연결 대신 로컬 context를 선택하고, 설정한 `DOCKER_HOST`가 있다면 원격 주소를 가리키는지 확인합니다.                                        |
| 같은 이름의 다른 Docker 네트워크가 있다는 안내 | `demo-local-test-loopback`의 설정 충돌입니다. 기존 네트워크는 자동 변경하지 않으므로 어떤 프로젝트가 만든 것인지 먼저 확인합니다.                                                                                   |
| 이미지 다운로드 또는 서버 건강 검사 실패       | 인터넷과 Docker Desktop의 메모리·디스크 여유를 확인한 뒤 `local:start`를 다시 실행합니다.                                                                                                                           |
| 테스트가 실패함                                | 표시된 실패 항목을 확인하고 `local:status`로 서버 상태를 봅니다. 처음 상태로 다시 검사하려면 가짜 자료 삭제를 이해한 뒤 `local:reset`을 사용합니다.                                                                 |

관리자 키나 로그인 토큰을 복사해 공유할 필요는 없습니다. 이 명령들은 로컬 연결 키를 내부에서 사용하고 상태 출력에는 주소와 컨테이너 상태를 보여 줍니다.

## 8. 파일이 맡은 일

| 경로                         | 역할                                                           |
| ---------------------------- | -------------------------------------------------------------- |
| `supabase/local/config.toml` | 프로젝트 ID, 포트, 로그인과 함수 실행의 로컬 전용 설정         |
| `scripts/local-test/`        | 명령 실행, 로컬 연결 제한, SQL 준비, 가짜 자료 생성, 통합 검증 |
| `artifacts/local-test/`      | CLI 작업 상태와 생성된 SQL·함수 번들 등 로컬 실행 산출물       |
| `database/cloud/`            | 업무 DB 원본과 동결한 버전. 로컬 준비는 동결판 체인을 사용     |

로컬 SQL은 `database/cloud/releases/`의 동결판으로 만듭니다. 기본층 설치 파일(`20261014-schema-control.json`) 하나를 `20261014000000_schema-control.sql`로 만들고, 이어서 데스크톱 후속판 체인(`20261014-multi-desktop`부터 최신 `20261022-schema-cleanup`까지)을 판마다 마이그레이션 파일 하나씩 만듭니다. 같은 날의 판은 그날의 다음 시간 번호(예: `20261018010000_work-routes.sql`, `20261018020000_work-sales-search.sql`)를 받아 출시 순서대로 적용됩니다. 원본 적용 목록은 `scripts/cloud-sql/sources.cjs`, 판 목록은 `scripts/cloud-sql/desktop-upgrades.cjs`에 있습니다. 과거 생성 마이그레이션이 남아 있거나 동일 파일의 내용이 다르면 준비를 중단하고 그대로 보존합니다. 기존 로컬 환경을 자동 초기화하지 않습니다. 검토된 전환 또는 별도 새 테스트 환경이 필요합니다. 자세한 절차는 [SQL 적용과 검증](sql-application.md)을 확인합니다.

개발 중 서버 SQL을 고쳐 둔 상태(동결판보다 앞선 상태)에서도 로컬 테스트 서버는 만들어집니다. 이때는 동결판 기준으로 만들고 "작업 중인 서버 SQL 변경은 들어가지 않는다"는 안내만 띄웁니다. 고친 SQL을 직접 보려면 `npm run dev:live`를 쓰면 작업 중인 SQL을 개발 서버에 그대로 적용합니다. "동결과 다르면 중단"하는 검사는 운영 서버용 파일을 만드는 `npm run cloud:build`에만 남아 있습니다.

Docker의 역할을 더 살펴보려면 [Docker 기본 개념](https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/), 로컬 서버 관리 흐름은 [Supabase CLI 개발 흐름](https://supabase.com/docs/guides/local-development/cli-workflows)을 참고하세요.

로컬 검사는 Realtime의 실제 PostgreSQL 구독 등록까지 기다리도록 설정했습니다. WebSocket 연결 완료만 확인하면 최초 서버 실행 때 변경이 먼저 발생해 알림 검사가 실패할 수 있기 때문입니다. 업무 앱의 연결 코드는 그대로 유지합니다.
