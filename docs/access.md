# 로그인과 직원 계정

## 공동 데스크톱 권한과 영업 배정

공동 고객 자료와 영업 배정 API는 데스크톱 역할(사장님·마스터·부마스터·관리자)이 아래 권한표의 기능 안에서 사용합니다. 최초 기준 DB 이전은 해당 회사 사장님만 실행합니다. 각 서버 요청은 실제 로그인 사용자·회사·존재하는 auth 세션을 확인하고, 쓰기 잠금을 기다린 뒤 권한을 다시 검사합니다. 데스크톱 창의 실행 ID와 배정 토큰은 메인 프로세스가 관리합니다. 화면이 전달한 다른 세션 ID/토큰으로 저장하지 않습니다.

확인 필요 배정을 강제로 해제할 때는 통화 종료 확인과 사유를 요구합니다. 재개 시 새 실행 ID와 회전한 토큰을 사용하여 복사된 초안/창이 같은 점유를 동시에 쓰지 못합니다. 일반 작업자의 휴대폰 조회에는 공유 원본 직접 쓰기·이전·영업 배정을 허용하지 않습니다.

## 권한

데스크톱에서 직원 권한을 선택하면 바로 저장합니다. 별도의 권한 저장 버튼은 없고, 저장이 끝나기 전에는 동기화 버튼을 사용할 수 없습니다. 저장 실패 시 이전 권한으로 되돌립니다.

역할 변경은 서버 access 알림, 앱 복귀·재연결, 최신 자료 확인 때 다시 검사합니다. 휴대폰을 쓸 수 없는 역할로 바뀌면 휴대폰에서 로그아웃합니다. 일반 작업자로 바뀌면 고객명 등 허용되지 않은 표시를 제거하고 해당 역할의 자료를 다시 받습니다. 업로드 등 진행 중 작업이 끝난 뒤 확인하며 주기적 권한 폴링은 하지 않습니다. 직원과 사장님·마스터 권한 그룹 사이 전환은 자료 보관 영역 확인을 위해 재로그인합니다.

역할은 6개입니다. 화면에 메뉴와 버튼을 보여 주는 기준은 `src/shared/access.cjs`, 실제 허용 여부는 서버의 `demo_desktop.role_allows`가 요청마다 다시 판단합니다. 관리자·부마스터 화면에서는 권한 없는 버튼이 흐리게 잠기고 눌러도 실행되지 않습니다.

| 일반 작업자 (`worker`) | 휴대폰                     | 회사 전체 작업 조회·검색, 지도 위치와 전화번호 확인, 배정된 작업의 사진 보고                                                                                                                                                                       |

**운영 서버는 다음 배포 전까지 이전 권한(사장님·마스터·관리자·일반 작업자, 관리자는 휴대폰 역할)으로 동작합니다.** 이 표는 개발 소스 기준이며 운영 반영 순서는 서버 적용 기록의 배포 대기를 따릅니다. 관리자·영업이 보낸 검토 요청은 [신규 등록 검토 요청함](data.md#신규-등록-검토-요청함)에 쌓이며, 승인하는 검토 화면은 아직 만드는 중입니다.

작업 사진은 배정 작업에서만 올리며, 배정 없는 보고는 역할과 관계없이 서버가 거절합니다. 사진 기능은 [R2 서버 설정](work-reports.md)을 적용해야 합니다. 일반 작업자에게는 고객명을 전달하지 않으며 계약, 금액, 청구, 입금 기록도 보내지 않습니다. 작업에서는 지역(순서), 구분 번호, 주소와 행 식별 정보만 제공합니다.

휴대폰은 사장님·마스터·일반 작업자만 로그인할 수 있습니다. 다른 역할은 "이 계정은 아직 휴대폰 앱을 사용할 수 없습니다" 안내가 나오고 로그인되지 않습니다. 메뉴는 고객 찾기·배정 작업(사장님·마스터는 작업 현황)·작업 확인·설정입니다. **작업 확인 → 보고 작업**은 회사 보고와 사진을 조회하는 공통 탭입니다. 휴대폰의 단독 **작업 보고** 등록 화면은 없앴습니다. **작업 확인 → 청구·입금 기록** 탭은 사장님·마스터만 볼 수 있고 일반 작업자의 접근과 조회 요청도 차단합니다. 별도의 묘지 지도 메뉴는 없으며, 고객 찾기의 **지도에서 보기**로 고객별 위치를 확인합니다. 직원 설정에는 최신 자료 다시 불러오기·로그아웃과 현재 계정 정보만 표시합니다. 모든 계정의 동기화·로그아웃 버튼은 설정 안에 있습니다.

데스크톱은 실행 즉시 로그인 화면을 표시하며, 데스크톱 역할(사장님·마스터·부마스터·관리자) 확인 전에는 고객 DB와 업무 기능에 접근할 수 없습니다. 영업은 고객 자료 없이 신규 등록 화면만 엽니다. 기존 회사의 프로젝트와 작업공간 연결을 확인합니다. 로그인하면 휴대폰 연동 창에서도 같은 로그인을 사용하며, 설정의 로그아웃을 누르면 연동 창을 닫고 시작 화면으로 돌아갑니다. 데스크톱 로그인 토큰은 프로그램 종료 시 지웁니다. 일반 작업자에게는 모바일 앱만, 부마스터·관리자·영업에게는 데스크톱만 배포합니다. 마스터는 발급받은 아이디로 데스크톱과 휴대폰 모두 로그인할 수 있습니다.

마스터는 기존 회사 소유 계정 아래의 별도 사용자입니다. 고객·청구·지도·작업 보고의 `owner_id`를 새 계정으로 옮기지 않습니다. 원래 사장님 계정은 직원 목록에 포함되지 않아 권한 변경·사용 중지 대상이 아닙니다. 마스터도 다른 직원·마스터의 권한을 바꿀 수 있지만 자기 계정의 권한 변경·사용 중지는 차단합니다. 부마스터는 자기보다 낮은 역할(관리자·영업·일반 작업자)만 만들고 바꾸고 중지합니다. 관리자는 관리자·영업·일반 작업자 계정만 목록에서 보고 이 세 역할의 새 아이디를 발급할 수 있으며, 기존 계정의 권한 변경·사용 중지·삭제는 할 수 없습니다(2026-10-29).

기존 서버의 SQL 업그레이드는 [SQL 적용과 검증](sql-application.md)을 따릅니다. `staff-accounts`, `work-reports` Edge Function은 최신 번들로 별도 배포합니다. 고객·입금 자료나 기존 직원 역할은 바꾸지 않습니다.

데스크톱은 회사 소유자 UUID로 로컬 DB를 고정합니다. 이전 버전의 이메일 연결은 첫 로그인에서 `demo_desktop_access`가 기존 회사 소유자 이메일과 비교한 뒤 UUID로 전환합니다. 이후 마스터·사장님 사이에서 로그인 사용자를 바꿔도 동일 회사의 자료에 연결됩니다.

## 기존 서버와 데스크톱 로그인 호환

2026-10-17: 공동 데스크톱·개인정보 전환 SQL이 아직 적용되지 않은 기존 서버에서, 새 RPC 부재가 계정 로그인 실패로 표시되던 경로를 수정했다. 사장님·마스터 인증 이후 새 상태/조회 RPC가 없으면 로그인 사용자의 RLS로 회사 식별자·revision·공동 전환 여부만 확인한다. 전환 전 회사임을 확인한 경우 기존 로컬 DB 방식으로 연다. 고객 본문은 이 확인에 사용하지 않으며, SQL 실행이나 회사 자료 이전을 자동 수행하지 않는다.

RPC 부재만으로 기존 방식을 허용하지 않는다. 회사 접근 거부·통신 오류·공동 전환 여부 불명·다른 회사 응답은 차단하며, 기존 공동 조회 사본을 로컬 원본으로 바꾸지 않는다. 이미 전환된 회사의 제한 조회·기기 정리·권한 검사는 유지한다. 실제 서버의 `demo_desktop_privacy_status`와 `demo_desktop_read`는 404/PGRST202로 부재함을 확인했다. 이 수정은 운영 SQL 적용 완료 기록을 바꾸지 않는다.

## 기존 회사 프로젝트에 적용

2026-10-01 적용 기록: 계정·마스터 권한 SQL과 `staff-accounts`·`work-reports` 함수를 배포하고, 기존 회사의 사장님 로그인·직원 목록·동기화 상태 조회를 확인했습니다. 실제 계정의 권한은 자동 변경하지 않았습니다. 직원 휴대폰 로그인은 발급한 계정으로 실제 기기에서 확인하며, 이후 화면 변경은 새 앱 설치로 반영합니다.

소스 변경만으로 Supabase의 권한이 바뀌지는 않습니다. 다른 프로젝트에는 아래 서버 적용 순서를 따릅니다.

1. [SQL 적용과 검증](sql-application.md)에서 새 빈 프로젝트 설치와 기존 프로젝트 기준 등록·업그레이드를 구분합니다.
2. 생성한 SQL 전체를 실행하고 verify 결과를 확인합니다. 개별 access 파일을 직접 재적용하지 않습니다.
3. 프로젝트 폴더에서 [Supabase CLI](https://supabase.com/docs/guides/functions/quickstart)로 로그인한 뒤 함수를 배포합니다.

```sh
npx supabase login
npx supabase functions deploy staff-accounts --project-ref 프로젝트ID
```

대시보드 편집기로 배포할 때는 `node scripts/build-server-function.cjs staff-accounts`를 실행하고, 생성된 `artifacts/server/staff-accounts/index.ts` 전체를 함수의 `index.ts`에 붙여넣습니다. 공통 처리기는 `src/server/staff-accounts-handler.mjs`에 있으므로 어댑터 원본 `index.ts`만 복사하지 않습니다. CLI는 저장소 루트에서 원본과 공통 모듈을 함께 묶습니다.

프로젝트 ID는 Supabase 프로젝트 URL의 첫 부분입니다. `supabase/config.toml`을 사용하는 프로젝트 루트에서 실행합니다. 함수는 `auth.getUser()`로 실제 사용자를 검증하고 `demo_access`로 사장님 권한을 다시 확인합니다. `verify_jwt=false`는 이 수동 검증 경로를 사용하기 위한 설정이며, 익명 계정 생성 API가 아닙니다. 관리자용 키는 함수의 서버 환경에만 존재하고 앱에 넣지 않습니다. [Supabase 인증 안내](https://supabase.com/docs/guides/functions/auth)

4. Supabase Authentication 설정에서 **Allow new users to sign up**을 끕니다. 직원은 앱의 회원가입 대신 사장님이 생성합니다.
5. 앱을 재시작하면 나오는 로그인 화면에서 기존 사장님 이메일·비밀번호로 로그인한 뒤 **설정 → 직원 계정 관리**를 엽니다.
6. 직원 이름, 아이디, 비밀번호(12자 이상), 역할(마스터·부마스터·관리자·영업·일반 작업자)을 선택해 생성합니다. 부마스터는 관리자·영업·일반 작업자만 고를 수 있습니다. 비밀번호는 생성 후 표시하거나 별도 저장하지 않습니다. 사장님이 직원에게 직접 전달합니다.

## 휴대폰

회사 연결 정보(프로젝트 URL, publishable/anon key, 작업공간 ID)는 루트 `.env`의 `DEMO_SUPABASE_URL`, `DEMO_SUPABASE_KEY`, `DEMO_WORKSPACE_ID`에서 모바일 빌드에 포함합니다. 새 기기에서도 사용자가 입력하지 않으며 로그인 화면에는 아이디 또는 이메일과 비밀번호만 표시합니다. 기존 설치의 연결 정보와 로그인 기록은 보존합니다. 서버 비밀 키나 계정 암호는 포함하지 않습니다. 직원은 발급받은 아이디·비밀번호로 로그인하면 허용된 자료를 자동으로 받습니다. 로그인은 로그아웃 전까지 유지하며 앱 복원 시 서버 권한을 확인하므로 인터넷 연결이 필요합니다. 오프라인이면 토큰을 보존하고 재연결 후 확인합니다.

- 직원 고객·지도 자료는 현재 실행 세션 메모리에 보관하고 앱 재실행 시 자동으로 받습니다. 로그아웃하면 로그인 토큰과 메모리 자료를 비웁니다. 사장님 계정의 기존 로컬 업무 기록·사진은 계정별로 유지합니다.
- 회사 PC의 고객·작업·지도 변경과 사장님·마스터의 확정 업무 기록은 자동 공유됩니다. 기존 순번·버전 비교를 사용하고 변하지 않은 자료 본문은 반복 전송하지 않습니다.
- 사용 중지는 서버의 다음 요청부터 적용됩니다. 이미 오프라인으로 열어 본 화면을 원격으로 즉시 지우지는 않습니다. 중지된 계정으로 재로그인·재동기화할 수 없습니다.
- 일반 작업자는 현재 배정된 작업 상세에서 위치 검색 없이 사진을 등록할 수 있습니다. 서버가 현재 배정·계정 상태를 등록과 완료 시 다시 확인합니다. 일반 작업자의 고객 정보 제한은 유지하며, 보고와 연결된 고객명은 고객을 볼 수 있는 계정에만 표시합니다.
- 작업 보고의 위치·보고자·사진은 회사 전체에 공유되며 **작업 확인 → 보고 작업**에서 조회합니다. 청구·입금 정보는 사장님·마스터만 **청구·입금 기록** 탭에서 접근합니다.
- 모바일 소스를 수정해도 설치된 APK가 바뀌지는 않습니다. `npm --prefix mobile run android:sync` 후 Android Studio에서 새 APK를 빌드하여 기존 앱 위에 설치합니다. 삭제 후 재설치하면 미동기화 로컬 기록이 없어질 수 있습니다.

## 신규 회사 최초 설정

이미 동기화한 현재 회사에는 이 단계가 필요 없습니다. 완전히 새 프로젝트는 생성한 `install.sql`을 적용한 뒤 Authentication → Users에서 사장님 계정을 관리자 권한으로 만들고, 데스크톱에 표시된 작업공간 ID를 확인합니다. SQL Editor에서 실제 두 UUID로 아래를 실행하면 로그인에 필요한 빈 작업공간만 준비됩니다.

```sql
select public.demo_provision_owner(
  '사장님 Auth 사용자 UUID'::uuid,
  '데스크톱 작업공간 UUID'::uuid
);
```

이 함수는 앱 사용자에게 실행 권한이 없고 SQL Editor에서만 실행합니다. 이미 있는 회사 자료를 덮어쓰지 않습니다. 이후 사장님 로그인 → 데스크톱 동기화로 실제 자료를 게시합니다.

## 이전 미연동 자료 보호

기기에 고객 자료가 있는데 어떤 회사 계정으로 연결했는지 기록이 없는 이전 버전은 사장님 로그인 시 연결을 중단합니다. 다른 계정으로 자료가 노출되거나 미전송 청구가 덮어써지는 것을 막기 위한 동작입니다. 앱을 삭제하거나 저장소를 초기화하지 말고, 해당 기기의 이전 자료와 원래 회사 계정을 확인해 이전해야 합니다. 이미 동기화를 정상 완료해 회사 계정 연결 기록이 있는 기기는 그대로 사용할 수 있습니다.

## 로그인 저장 방식

Android는 Android Keystore의 AES-GCM 키로 로그인 토큰을 암호화해 앱 전용 저장소에 보관합니다. 비밀번호는 저장하지 않으며 Android 백업도 허용하지 않습니다. 브라우저 개발 미리보기는 해당 브라우저의 IndexedDB를 사용합니다. 계정 사용 중지·서버 세션 취소 등으로 인증이 무효가 되면 다시 로그인해야 합니다. 일시적인 동기화 통신 오류는 저장된 로그인을 삭제하지 않습니다.

## 직원 자료 자동 공유

일반 작업자를 포함한 모든 계정은 서버 변경 알림과 앱 실행·복귀 시 자료를 자동으로 확인합니다. 직원 계정 관리에는 별도 동기화 버튼이나 수동 요청 상태 열을 표시하지 않습니다.

연결 문제를 확인할 때만 각 기기의 **설정 → 최신 자료 다시 불러오기**를 사용합니다. 회사·역할별 접근 권한은 동일하게 적용됩니다. 종료된 앱을 강제로 실행하지는 않습니다.

구버전 호환을 위한 `database/cloud/staff-sync.sql`의 기기별 수신 확인 API(`demo_check_staff_sync`·`demo_finish_staff_sync`)만 유지합니다. 요청 API(`demo_request_staff_sync`·`demo_staff_sync_status`)는 `20261022-schema-cleanup`에서 제거했습니다. 최신 화면에서는 수동 요청을 만들지 않습니다.

## 직원 계정 삭제

데스크톱 **설정 → 직원 계정 관리 → 계정 삭제**에서 이름·아이디와 확인 안내를 보고 삭제합니다. 사장님과 마스터만 실행할 수 있으며, 원본 사장님 계정과 로그인 중인 본인 계정은 서버에서도 차단합니다. 서버가 확인한 회사의 직원에게만 적용합니다.

삭제는 `demo_members.active=false`로 먼저 접근을 막은 뒤 Supabase Auth 사용자를 실제 삭제합니다. 직원 명부와 기기 동기화 수신 기록은 함께 제거됩니다. 회사의 작업 보고·사진·보고자 이름·고객·청구·입금은 남습니다. 보고의 `reporter_id`만 NULL이 되고 `reporter_name` 및 사진 메타데이터·R2 객체 경로는 유지됩니다. 삭제된 보고자의 보고를 다른 사용자가 업로드 재시도로 가로챌 수 없습니다.

Auth 삭제에 실패하면 계정은 사용 중지 상태로 남으며 앱에서 다시 삭제할 수 있습니다. 삭제된 로그인 계정은 복원되지 않습니다. 이미 내려받아 열린 화면을 원격으로 지우지는 않지만 다음 서버 접근과 재로그인은 거부됩니다.

직원 삭제를 위한 보고자 FK는 현재 설치 버전에 포함되어 있습니다. 기존 서버 변경은 [SQL 적용과 검증](sql-application.md)을 따르고 `staff-accounts` 함수는 별도로 배포합니다. 데스크톱 변경은 앱 재실행 후 반영됩니다.

예전 현장 관리자(`manager`) 역할과 그 고객명 표시는 권한 재설계에서 없앴습니다. 현재 서버의 정의·버전은 생성한 verify SQL로 확인합니다.
