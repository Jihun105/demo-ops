# 고객 일반 삭제 보존 · 영구삭제 전체 제거

상태: 사용자 요구 범위 확인 완료, 구현 전 설계 검토 대기

## 1. 사용자가 정한 규칙

- 신규 등록은 현재 입력·고객 번호 발급 흐름을 유지한다.
- 일반 삭제는 삭제 목록으로 옮기는 처리다. 고객과 관련 자료를 그대로 유지하고 복원할 수 있다.
- 영구삭제는 해당 고객의 연결 자료를 앱이 관리하는 저장소에서 제거한다.
- 제거 대상에는 고객·묘지·금액·연간 작업·배정·위치, 청구·입금·문자 원문과 발송 기록, 작업 보고·사진·KML/KMZ, 기기 사본·작성 초안, 앱 자동 백업 속 고객 자료까지 포함한다.
- 청구·입금을 별도 보존한다는 현재 영구삭제 규칙을 이 요청에 대해서는 폐기한다.
- 다른 고객의 자료는 보존한다. 이름·주소가 같다는 이유로 다른 고객의 자료를 삭제하지 않는다.

## 2. 현재 코드에서 바뀌는 부분

현재 `database/cloud/privacy/deletion.sql`의 `permanent_delete`는 금융 자료를 분리 보관하고 회사의 자료 세대를 갱신한다. PC와 휴대폰 정리 과정도 보존된 금융 조회 결과를 이용해 연결 자료를 찾는다. 자동 DB 백업 속 고객 원문은 현재 이 경로로 제거되지 않는다.

따라서 SQL의 금융 보존 호출 하나만 제거하면 안 된다. 먼저 삭제 대상 ID를 확정하고 파일·기기 정리에 필요한 최소 식별 정보를 전달한 뒤, 원문을 제거해야 한다. 기존 세대 갱신과 구형 쓰기 차단은 늦게 연결된 기기가 삭제 자료를 다시 올리지 못하도록 유지한다.

이 작업은 기존 고객 삭제 흐름을 변경하지만, 서버·PC·휴대폰 사이의 정리 계약과 백업 처리도 함께 바뀌므로 구조 변경으로 취급한다.

## 3. 삭제 대상 결정

삭제 목록에 있는 고객의 ID와 연결 묘지 ID를 기준으로 범위를 고정한다. 미연결 묘지를 영구삭제하는 기존 기능은 선택한 묘지 ID로 한정한다.

삭제 실행 전에 같은 회사 범위에서 다음 연결을 수집한다.

| 대상                                           | 연결 기준                                               |
| ---------------------------------------------- | ------------------------------------------------------- |
| 고객·묘지·연도별 금액·작업·위치·작업 순서/배정 | 고객 ID, 묘지 ID, 작업 key                              |
| 청구와 발송·입금·취소 이벤트                   | 고객/묘지에 속한 청구 ID와 그 청구를 참조하는 이벤트 ID |
| 입금 문자와 금융 보관 자료                     | 청구/입금 연결, 금융 증빙 색인, 원본 수신 ID            |
| 작업 보고·사진                                 | 청구의 보고 ID 또는 배정 작업의 정확한 보고 연결        |
| KML/KMZ와 임시 업로드                          | 묘지 ID, 자산 버전 ID, 원문 해시                        |
| 초안·요청 기록·기기 사진·발송 사본             | 위 ID 집합과 명시적인 로컬 연결                         |
| 앱 자동 백업                                   | 백업 내부의 회사 ID와 위 고객/묘지/업무 ID              |

문자열 이름·동일 주소·동일 금액만으로 삭제 대상을 확대하지 않는다. 다른 고객이 일반 삭제 또는 거절 목록에 있어도 그 고객의 자료는 보존 대상이다.

다른 고객도 참조하는 파일은 공유 여부를 먼저 확인한다. 대상 고객의 전용 사본과 연결은 제거하지만, 공용 원본을 임의로 삭제하지 않는다. 고객별 내용을 분리할 수 없는 공용 원본은 확인 필요로 남기며 전체 삭제 완료로 표시하지 않는다.

## 4. 서버 처리

1. 로그인·회사·역할·수정 버전·삭제 목록 상태를 검증한다.
2. 회사 쓰기 잠금 안에서 삭제 범위와 중복 요청 번호를 고정한다.
3. 보고·자산·기기 정리에 필요한 ID만 삭제 작업에 등록한다. 원문을 정리 작업 기록에 복사하지 않는다.
4. 고객의 운영 행, 연결된 금융 원본/증빙/상대 식별/해당 증빙 접근 기록을 제거한다. 다른 고객의 행 내용은 유지한다.
5. 과거 전송 사본과 요청 결과에서 고객 원문이 남지 않게 정리하고 새 자료 세대로 전환한다.
6. 조회 자료와 금융 합계를 재생성한다. 같은 삭제 요청이 재전송돼도 중복 처리하거나 다른 고객을 대상으로 삼지 않는다.

R2 파일 삭제는 DB 트랜잭션과 별도 작업이다. 기존 삭제 작업·재시도 경로를 재사용하며, 해당 고객 전용 파일은 회계 분류 승인을 기다리지 않고 제거 대상으로 확정한다. 발급된 업로드 URL과 진행 중 업로드가 파일을 되살리는 경우까지 검증한 뒤 완료한다. 실제 객체 제거에 실패하면 정리 중 상태를 유지한다.

과거 동결 배포 JSON은 수정하지 않는다. 검증 후 새 후속 배포를 만들고 직전 버전에서의 업그레이드와 새 시험 서버 설치를 모두 확인한다. 배포만으로 과거에 영구삭제된 고객의 보관 증빙을 일괄 제거하지 않는다. 기존 자료의 소급 삭제는 이 구현 작업에서 자동 실행하지 않는다.

## 5. PC·휴대폰 사본

삭제 후 금융 조회에서 청구가 사라져도 정리 대상을 찾을 수 있도록 삭제 작업에 청구·보고·이벤트 ID 집합을 전달한다. PC/휴대폰은 새 조회 자료를 설치한 뒤 해당 고객의 캐시·초안·요청 원문·사진 사본·발송 사본을 정리한다.

- 삭제 고객에 대한 미전송 입력은 재전송하지 않고 제거한다.
- 다른 고객의 미전송 입력은 유지한다.
- 이미 진행 중인 실제 문자 전송 등 즉시 중단 여부를 확인할 수 없는 처리는 완료 여부를 확인할 때까지 정리 중으로 남긴다.
- 정리되지 않은 구버전 기기는 삭제 자료의 재게시를 허용하지 않는다.
- 오프라인 기기는 다음 접속 때 처리한다. 접속하지 않은 기기의 사본을 원격으로 지웠다고 표시하지 않는다.
- 정리를 완료한 PC의 일반 등록·저장은 다른 오프라인 기기의 정리 완료를 기다리지 않는다.

실제 수신인의 휴대폰, OS 문자함, 사용자가 별도로 복사한 파일은 앱 소유 저장소가 아니다. 이 기능이 삭제 완료를 보장하는 범위에 포함하지 않는다.

## 6. 자동 백업

앱이 생성하고 관리하는 자동 백업을 회사·원본 DB별로 식별한다. 여러 고객이 들어 있는 백업 파일 전체를 지우지 않는다.

각 백업은 임시 사본에서 해당 고객의 연결 자료만 제거하고, SQLite 무결성·외래 키·다른 고객 행 내용의 동일성을 검사한 다음 원자적으로 교체한다. 삭제된 원문이 SQLite 빈 페이지에 남지 않도록 새 파일로 재구성한다. 자동 백업에 함께 보관된 해당 고객의 파일 사본도 정확한 연결과 해시를 확인해 정리한다.

알 수 없는 백업 형식, 읽기 실패, 회사 식별 불일치, 디스크 부족 또는 교체 실패는 완료로 처리하지 않는다. 관련 백업이 남으면 정리 중/확인 필요를 표시한다.

사용자가 별도로 내보낸 파일·수동 복사본, 앱이 관리하지 않는 외부 저장소와 서비스 제공자의 DB 스냅샷은 자동 삭제 완료를 보장할 수 없다. 앱의 자동 백업과 이러한 외부 사본을 혼동하지 않게 표시한다.

## 7. 화면 동작

- 일반 삭제 안내: 삭제 목록에서 자료를 그대로 확인하고 복원할 수 있음.
- 영구삭제 확인: 청구·입금·문자·사진·파일·자동 백업 속 해당 고객 자료까지 제거하며 복원할 수 없음을 표시.
- 고객 DB에서 제거된 시점과 모든 관리 사본의 정리가 끝난 시점을 구분한다.
- 파일·백업·오프라인 기기가 남으면 `고객 삭제 완료 · 관련 자료 정리 중`으로 표시한다.
- 확인된 관리 대상의 정리가 모두 끝났을 때 `영구삭제 완료`를 표시한다.

## 8. 검증 기준

먼저 가짜 자료로 기존 보존 동작 때문에 실패하는 검사를 작성하고, 구현 후 같은 검사가 통과하는지 확인한다.

1. 신규 등록 → 일반 삭제 → 복원: 관련 행·원문·파일 내용이 유지된다.
2. 다시 삭제 → 영구삭제: 대상 고객의 운영/금융 원문과 전용 파일이 사라진다.
3. 다른 고객, 같은 이름/주소의 고객, 일반 삭제 목록의 다른 고객과 그 금융·파일 자료는 유지된다.
4. 같은 영구삭제 요청의 반복과 중간 실패 재시도가 안전하게 끝난다.
5. 영구삭제 후 새 자료를 받은 PC에서 신규 등록·수정이 정상 작동한다.
6. 오프라인/구형 기기의 오래된 입력이 삭제 자료를 복원하지 않는다.
7. 자동 백업을 복원해도 삭제 고객이 돌아오지 않고 다른 고객의 자료는 동일하다.
8. R2·백업 교체·기기 사본 정리 실패를 성공으로 표시하지 않는다.
9. 기존 전체 테스트를 실행하고 정책 변경에 따른 기대 결과를 명시적으로 갱신한다.

## 9. 이번 작업의 실행 경계

구현과 시험에서는 운영 고객의 실제 영구삭제를 실행하지 않는다. 새 SQL·서버 함수·PC 및 휴대폰 배포본을 검증한 뒤 적용 결과를 구분해 안내한다. 운영 배포와 기존 실자료의 삭제는 준비된 변경·대상·검증 결과를 확인하는 별도 최종 단계다.
