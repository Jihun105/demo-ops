# R2 사진·KML 저장·보관·삭제 설계

상태: 2026-10-22 사용자 결정을 반영한 설계. 3단계 구현 완료(개발 서버에서 확인, 백업 관련 부분은 NAS 보류로 제외, 7장 끝 구현 상태 참고), 운영 반영은 2-6과 함께 대기.

## 1. 목적과 사용자 결정

R2에 들어가는 작업 사진과 Google Earth 원본(KML/KMZ)이 언제 생기고, 어디에 놓이고, 언제 지워지는지를 하나의 규칙으로 정한다. 회사 NAS 백업을 되돌리기 수단으로 사용하고, R2에는 업무에 필요한 현재 파일만 남긴다.

2026-10-22 사용자 결정:

- 묘지별 최신 2건을 넘어 밀려난 작업 사진과 교체된 이전 KML은 사람의 분류 확인 없이 자동 삭제한다. 실수로 교체한 경우의 되돌리기는 회사 백업으로 해결한다.
- 고객 영구삭제 시 해당 고객의 사진·KML도 분류 확인 없이 모두 자동 삭제한다. 2026-10-20 [영구삭제 전체 제거 설계](2026-10-20-customer-permanent-purge-design.md)와 같은 방향이다.
- 회사 NAS 백업은 영구삭제한 고객의 파일을 포함해 **모든 파일을 무조건 1년 보관**한다.
- 사진은 세무 증빙 보관 의무 때문이 아니라 만일에 대비해 남기려는 것이다. R2에서 지운 사진도 NAS 백업에서 1년간 꺼내 볼 수 있으면 충분하다.
- 한 묘지의 작업 사진과 위치 자료(KML·스크린샷)는 같은 묘지 폴더에 모은다.
- 설계 문서는 이 저장소에 둔다.
- R2도 사람이 열어 보는 폴더처럼 **지역 → 시·군 → 묘지 번호** 구조로 정리한다. 한글 폴더명 관리 부담은 감수하고 4장의 규칙으로 막는다. 지역이 바뀌어도 파일은 옮기지 않는다(2026-10-22 결정, 4장).
- **2026-10-22: NAS 백업 전면 보류, 백업 없이 자동 삭제 진행(사용자 결정).** 백업이 생길 때까지 5장 삭제 조건 3·4번(백업 확인)은 적용하지 않고, 1·2번(6분 안전 대기, 다른 참조 없음)만 만족하면 지운다. **지운 파일은 되찾을 수 없다.** 백업이 생기면 3·4번을 다시 켠다.
- NAS 백업에는 **DB에 등록(승인)된 자료만** 넣는다. 검토 대기·작성 중 자료는 백업하지 않는다. 서버 DB 백업(Supabase 덤프)에서도 등록 요청함 표의 데이터는 제외한다([권한 설계](2026-10-22-role-permissions-design.md) 4.3).

2026-10-22 추가 결정에 따라 KML 가져오기 흐름은 [묘지 위치·경계 입력 재설계](2026-10-22-kml-location-design.md)에서 다시 정하고, 이 문서는 그 결과(위치 이미지 `earth.jpg` 포함)를 반영한다. 청구·입금 기록 구조는 별도 설계로 다시 정한다.

이 결정으로 2026-10-15 [전송 최소화·보존 설계](2026-10-15-data-minimization-retention-design.md) 6장의 "작업 사진을 증빙/업무 사본으로 분류한 뒤 정리" 규칙은 R2 사진·KML에 한해 이 문서로 대체한다. 청구·입금 기록 자체의 보존 규칙은 바꾸지 않는다. 사진을 세무 증빙으로 별도 보관할 의무가 있는지는 회사가 확인할 사항이며, 이 설계가 법적 판단을 대신하지 않는다.

## 2. 현재 구조 (2026-10-22 소스 기준)

운영 회사는 공동 모드(shared)와 개인정보 보존 모드(privacy protocol 2, 2026-10-20 전환)를 사용한다. 아래는 그 경로의 동작이다. 보존 모드 이전 경로(직접 정식 경로 PUT, `report-photo-retention.sql`의 단독 정리)는 소스에 남아 있지만 운영 회사에서는 쓰지 않는다.

### 객체 종류와 경로

| 종류             | R2 경로                                                                 | 만료 규칙             |
| ---------------- | ----------------------------------------------------------------------- | --------------------- |
| 사진 임시 업로드 | `report-staging/{ownerId}/{workspaceId}/{reportId}/{photoId}.jpg`       | 1일 (2026-10-20 설정) |
| 사진 정식        | `{ownerId}/{workspaceId}/{reportId}/{photoId}.jpg` (버킷 최상위)        | 없음                  |
| KML 임시 업로드  | `earth-staging/{workspaceId}/{graveId}/{versionId}/original.{kml\|kmz}` | 1일 (2026-10-20 설정) |
| KML 정식 원본    | `earth/{workspaceId}/{graveId}/{versionId}/original.{kml\|kmz}`         | 없음                  |
| KML 설명         | `earth/{workspaceId}/{graveId}/{versionId}/manifest.json`               | 없음                  |

객체 경로는 서버가 ID로 계산한다(`work-reports-handler.mjs`의 `path`, `earth-assets-handler.mjs`의 `prefix`, `privacy-assets.mjs`의 정리 키). DB에는 경로 문자열을 저장하지 않는다. 앱은 서명 URL의 호스트(`*.r2.cloudflarestorage.com`)만 검사하고 경로 형식은 검사하지 않는다.

### 업로드

- 사진: `begin`에서 보고 예약과 용량 예약(전체 8GB) → 5분 서명 PUT으로 임시 경로에 업로드(크기·`image/jpeg` 서명 포함) → `finish`에서 서버가 임시 바이트를 읽어 크기·JPEG 시작 바이트·SHA-256 확인 → 정식 경로에 `If-None-Match: *`로 한 번만 저장(메타데이터 `sha256`) → 보고 공개 → 임시 파일 삭제 시도.
- KML: `begin`에서 후보/버전 예약 → 5분 서명 PUT으로 임시 경로 업로드 → `finish`에서 크기·종류·SHA-256 확인 → 정식 원본과 `manifest.json` 저장 → `ready` 공개 → 임시 파일 삭제 시도. 24시간 동안 연결되지 않은 후보는 취소된다.
- 조회: 서버가 5분짜리 서명 GET을 발급한다. 영구 공개 주소는 없다.

### 보관과 삭제

- 사진: 보고 공개 때 같은 묘지(`retention_key`)의 공개 보고를 최신순으로 세어 3번째부터 `photo_state='pruning'`으로 표시한다.
- KML: 묘지 연결이 다른 버전으로 바뀌거나 묘지가 삭제되면 이전 버전을 `earth_cleanup`에 넣는다.
- 보존 모드에서는 위 대상과 영구삭제 대상이 `privacy_media`(분류 기본값 `unclassified`)와 `privacy_cleanup_jobs`(`blocked`)로 등록된다. 정리 함수는 분류가 `operational`인 항목만 지운다. 설정 화면에서 사람이 한 건씩 "업무 사본"으로 확인해야 R2 삭제가 진행된다.
- 삭제는 퇴역 표시(`eligible_at`) 후 6분이 지난 항목만 실행한다. 이미 발급된 5분짜리 업로드 URL과 진행 중인 `finish`가 파일을 되살리는 것을 막기 위해서다.
- 정리는 보고 목록 조회·보고 등록(`work-reports`)과 데스크톱 동기화의 `earth.cleanup` 호출 때만 실행된다. 예약 실행은 없다.

### 확인된 문제

1. 보존 모드 전환 이후 자동 정리가 사실상 멈췄다. 분류 확인 전까지 밀려난 사진·이전 KML·영구삭제 대상이 R2에 계속 남는다. `work-reports.md`의 "최신 2건만 보관" 설명과 실제 동작이 다르다.
2. 삭제되지 않은 사진의 `total_bytes`가 8GB 예산에 계속 잡힌다.
3. 완료되지 않은 보고 예약은 임시 파일이 1일 뒤 사라져도 DB 예약 용량이 영구히 남는다(`work-reports.md` "미완료 예약/사진의 자동 삭제는 없습니다").
4. 사진 정식 경로에 접두사가 없어 버킷 최상위에 놓인다. 백업 범위·만료 규칙·용량 점검을 접두사로 지정할 수 없고, 다른 용도의 객체가 생기면 구분이 어렵다.
5. DB 기록과 R2 객체를 대조하는 점검이 없다. DB에 없는 R2 객체(고아)나 R2에 없는 DB 기록(누락)을 찾지 못한다.
6. 정리가 사용자 활동에 의존한다. 앱을 오래 쓰지 않으면 정리도 멈춘다.
7. `manifest.json`에 당시 주소·파일명·geometry·좌표가 들어 있어 R2와 그 백업이 개인정보 사본이 된다.
8. R2 백업이 없다. 따라서 지금 자동 삭제를 켜면 되돌릴 방법이 없다.
9. `claim_cleanup_jobs`는 완료되지 않은 작업을 `checked_at` 순으로 최대 100개 읽는데, 보류 처리 때 `checked_at`을 갱신하지 않는다. 보류 건이 100개를 넘으면 매번 같은 보류 건만 읽고 새 정리 대상에 도달하지 못할 수 있다. 새 규칙에서는 보류 상태를 없애고, 재시도 때도 `checked_at`을 갱신한다.

## 3. 원칙

- **DB가 기준이다.** 어떤 파일이 있어야 하는지는 DB가 정하고, R2는 그 바이트만 보관한다. R2에만 있는 파일은 고아로 취급한다.
- **경로는 사람이 읽을 수 있게, 연결은 DB가.** 경로에 지역·시군·묘지 번호를 넣어 사람이 찾기 쉽게 한다. 다만 경로는 바뀔 수 있으므로 앱은 경로를 계산하지 않고 DB에 저장된 실제 키만 쓴다.
- **백업이 확인되기 전에는 지우지 않는다.** 자동 삭제의 안전장치는 사람의 분류 확인이 아니라 확인된 회사 백업이다.
- **백업은 1년, 예외 없음.** 교체·영구삭제·고아 정리로 R2에서 지운 파일도 NAS 백업에는 1년 남은 뒤 만료된다. 다만 일반 복구 절차는 영구삭제한 고객을 되살리지 않는다. 영구삭제 고객 파일을 꺼내는 일은 사장님이 직접 판단하는 예외 작업이다.

## 4. 새 경로 규칙

### 구조

```text
{workspaceId}/묘지/{사업지역}/{시군}/{묘지번호}/
├── 위치/{저장일}_{버전ID}/      original.kml · earth.jpg · manifest.json
└── 작업사진/{보고일}_{보고ID}/  01_{사진ID}.jpg · 02_{사진ID}.jpg …
{workspaceId}/미연결/작업사진/{보고일}_{보고ID}/…   묘지를 정하지 못한 보고
staging/{workspaceId}/{업로드ID}/…                    업로드 임시 칸, 1일 자동 만료
review/{workspaceId}/{요청ID}/original.kml|earth.jpg|manifest.json   신규 등록 검토 대기 칸, 자동 만료 없음
```

예: `fe1c21e5-…/묘지/경기북부/파주시/328/위치/2026-10-22_3f9a…/original.kml`

- 정식 자료는 `{workspaceId}/` 아래에만 둔다. 최상위에는 이것과 `staging/`, `review/`만 허용하고, 다른 최상위 객체는 점검에서 고아로 보고한다.
- "현재/이전"은 경로에 넣지 않는다. 어느 버전이 현재인지는 DB가 정한다. 경로에 넣으면 교체할 때마다 파일을 옮겨야 하기 때문이다.
- 2026-10-22 사용자 결정으로 배정 없는 작업 보고를 없애므로, 새 보고 사진은 항상 배정 작업의 묘지 폴더에 들어간다. `미연결/`은 이전에 배정 없이 올라온 보고(묘지를 확정하지 못한 것)를 옮길 때만 쓴다.

### 실제 키는 DB에 저장한다

- 서버가 객체마다 실제 키·크기·SHA-256·종류(원본/스크린샷/사진)·묘지/보고/버전 ID를 **객체 목록 표**에 기록한다. 조회 URL 발급·삭제·점검·백업 확인은 모두 이 표의 키를 쓴다.
- 키는 서버만 만든다. 앱이나 사람이 키를 조립하지 않는다.
- 사람이 R2 화면에서 직접 지우거나 옮기지 않는다. 그렇게 하면 표와 어긋나며, 7장의 점검이 "누락"으로 잡아낸다.

### 지역이 바뀌어도 옮기지 않는다

2026-10-22 사용자 결정: 묘지의 사업지역·주소를 고치는 일은 없다고 보고, **지역이 바뀌어도 파일을 새 폴더로 옮기지 않는다.**

- 폴더 이름은 파일을 **올린 시점의 지역**이다. 앱은 폴더 이름이 아니라 DB의 객체 목록에 적힌 키로 파일을 찾으므로, 지역이 바뀌어도 사진·KML은 계속 보인다.
- 지역이 바뀐 묘지는 예전 폴더에 남고, 그 뒤에 올리는 파일만 새 지역 폴더에 들어간다. 사람이 R2를 열어 볼 때 일부 묘지가 예전 지역 이름 아래 있을 수 있다.
- 지역 변경이 잦아져 불편해지면 그때 "새 키로 복사 → 크기·SHA-256 확인 → DB 키 교체 → 6분 뒤 이전 키 삭제" 방식의 이동 작업을 추가한다. 객체 목록 표가 이미 실제 키를 가지므로 나중에 추가해도 구조를 바꿀 필요가 없다.
- 묘지를 정하지 못해 `미연결/`에 올라간 보고 사진도 옮기지 않는다. 2026-10-22 결정으로 새 보고는 항상 배정 작업의 묘지 폴더에 들어간다.

### 한글 폴더명 규칙

| 위험                                                                              | 대응                                                                                              |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Mac과 Windows·Android의 한글 저장 방식 차이(NFD/NFC)로 같은 이름이 다른 폴더가 됨 | 서버가 키를 만들 때 항상 NFC로 정규화한다. 파일 이름·사용자 입력으로 키를 만들지 않는다           |
| 같은 지역을 다르게 적음(경기 북부/경기북부, 파주/파주시)                          | 사업지역·시군 이름은 정해진 목록에서만 고른다. 목록에 없으면 `미분류`                             |
| 공백·특수문자로 인한 주소 인코딩 문제                                             | 한글 폴더명에 공백·특수문자를 쓰지 않는다(`경기북부`)                                             |
| 서명 URL의 한글 인코딩                                                            | AWS SDK가 처리한다. 출시 전에 PC(Mac·Windows)·Android·iPhone에서 한글 키의 업로드·조회를 시험한다 |
| 백업·NAS 도구의 한글 처리                                                         | rclone과 NAS 공유폴더에서 Mac·Windows로 열어 보고 폴더가 하나로 보이는지 시험한다                 |

한글은 `묘지`, `미연결`, `위치`, `작업사진`과 사업지역·시군 폴더에만 쓴다. 파일 이름·ID·임시 칸(`staging/`, `review/`)은 영문·숫자만 쓴다.

### 그 밖의 규칙

- 회사 격리는 경로가 아니라 서버 권한 검사로 보장한다.
- 버킷 CORS와 앱의 허용 호스트는 바뀌지 않는다. 앱 재설치 없이 서버 함수 배포와 객체 이전만 필요하다.
- 폴더명에 고객 이름·전화번호를 넣지 않는다.

## 5. 생명주기

한 파일은 DB의 한 항목(`privacy_media` 또는 보고/자산 행)과 1:1로 대응하며 아래 순서로만 이동한다.

| 단계      | 의미                                             | R2 객체                 |
| --------- | ------------------------------------------------ | ----------------------- |
| 예약      | 서버가 ID·크기를 예약하고 업로드 URL 발급        | 임시 경로(있을 수 있음) |
| 보관      | 서버 검증을 통과해 정식 경로에 저장, 앱에서 사용 | 정식 경로               |
| 퇴역      | 교체·영구삭제·예약 만료로 더 이상 쓰지 않음      | 정식 경로(아직 남음)    |
| 삭제 대기 | 6분 안전 대기와 백업 확인을 기다림               | 정식 경로               |
| 삭제 중   | R2 삭제 실행·재시도                              | 일부 남을 수 있음       |
| 삭제 완료 | 모든 관련 키 삭제 확인, 예약 용량 반환           | 없음                    |

단계를 건너뛰거나 거꾸로 가지 않는다. 퇴역한 항목에 늦은 업로드가 도착하면 기존 `rearm_media`처럼 삭제 대기로 되돌려 다시 지운다.

### 퇴역 조건

| 대상                     | 퇴역 시점                                                                                                                    |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- |
| 작업 사진                | 같은 묘지의 공개 보고 중 최신 2건 밖으로 밀려났을 때 (보고 기록·청구·입금 이력은 유지, 사진만 퇴역)                          |
| 이전 KML                 | 묘지 연결이 새 버전으로 바뀌었을 때, 또는 연결되지 않은 후보가 24시간 지났을 때                                              |
| 영구삭제 고객의 사진·KML | 영구삭제 트랜잭션이 커밋됐을 때 (2026-10-20 설계의 삭제 범위)                                                                |
| 미완료 보고 예약         | 예약 후 7일 동안 공개되지 않았을 때. 예약 용량을 반환하며 기기의 초안은 그대로 둔다. 이후 등록 재시도는 새 예약으로 처리한다 |
| 임시 업로드              | R2 만료 규칙 1일 (유지)                                                                                                      |

### 삭제 조건

퇴역한 항목은 다음을 모두 만족할 때 사람 확인 없이 삭제한다.

1. 퇴역 표시 후 6분이 지났다(늦은 서명 PUT·진행 중 `finish` 차단, 현행 `eligible_at` 유지).
2. 현재 다른 묘지·보고·고객이 같은 객체를 참조하지 않는다(현행 `earth_links` 등 참조 검사 유지).
3. **백업 확인**: 그 객체의 정식 저장 시각이 마지막 성공 백업의 시작 시각보다 이르다. 즉 그 파일이 백업에 들어간 것이 확인됐다.
4. 마지막 성공 백업이 48시간 이내다. 백업이 멈추면 자동 삭제도 멈추고 설정 화면에 "백업 확인 대기"를 표시한다.

영구삭제 대상도 3·4번 조건을 따른다. 영구삭제의 R2 정리는 DB 커밋 이후 별도 작업이라는 2026-10-20 설계와 같다. DB에서 고객이 사라진 시점과 파일 정리가 끝난 시점을 구분해 표시한다.

현행 `classification` 항목은 자동 정리 대상을 기본 `operational`로 등록하도록 바꾼다. `blocked/policy-review/retention-review` 상태로 등록하지 않는다. 설정의 분류 화면은 이 전환 이후 쌓인 기존 보류 건을 처리한 뒤 제거한다.

"즉시 삭제"는 실제로 **다음 백업이 성공한 직후**를 뜻한다. 하루 한 번 백업하면 퇴역 후 길어야 약 하루 안에 지워진다.

## 6. 백업 연동

### NAS 백업 작업

- NAS(사내망)에서 R2를 읽어 오는 방향으로만 동작한다. NAS를 인터넷에 공개하지 않는다.
- R2 토큰은 이 버킷의 읽기 전용 토큰을 따로 발급한다. 서버 함수의 읽기·쓰기 토큰과 공유하지 않는다.
- 하루 1회 `{workspaceId}/` 아래 정식 자료만 백업한다. `staging/`(임시)과 `review/`(검토 대기)는 제외한다. DB에 등록(승인)된 자료만 백업한다는 사용자 결정에 따른 것이다.
- R2 구조가 이미 사람이 보는 폴더 구조이므로 NAS에는 같은 구조를 그대로 복사한다. 별도의 보기 폴더를 만들지 않는다.
- 삭제가 R2에서 일어나도 백업에서는 바로 지우지 않는다. 예: `rclone sync --backup-dir`로 R2에서 사라진 파일을 날짜별 보관 폴더로 옮기고, 1년이 지난 날짜 폴더를 지운다. QNAP HBS 3의 버전 보관도 같은 조건을 만족하면 사용할 수 있다.
- 백업 폴더는 암호화하고 접근 계정을 사장님과 지정 관리자로 제한한다. 사진·`manifest.json`에 개인정보가 들어 있기 때문이다.

### 백업 확인 기록

- 백업 작업은 끝난 뒤 객체 수·바이트·대상 키 목록의 해시를 검증하고, 성공했을 때만 서버에 확인 기록(시작 시각, 완료 시각, 객체 수, 바이트, 목록 해시)을 남긴다.
- 확인 기록 전용 서버 함수와 전용 토큰을 사용한다. 이 토큰은 기록 추가만 할 수 있고 업무 자료·서명 URL·삭제 기능에는 접근할 수 없다.
- 확인 기록이 성공하면 같은 호출에서 정리 작업을 실행할 수 있다. 백업 → 정리 순서가 자연스럽게 유지되고, 사용자가 앱을 열지 않아도 하루 한 번 정리된다(문제 6 해결). 기존 보고 조회·동기화 때의 정리도 유지하며, 이때도 같은 삭제 조건을 사용한다.
- 정리 작업은 지금의 사용자 세션 기반 함수(`media_actor`의 `auth.sessions` 검사)를 쓸 수 없다. 회사 범위로 제한된 서버 전용 정리 경로를 따로 만들어야 하며 구현 계획에서 권한 경계를 정한다.

### 영구삭제와 백업

영구삭제 고객의 파일도 R2에서는 자동 삭제하고, NAS 백업에서는 다른 파일과 똑같이 날짜별 보관 폴더로 옮겨 1년 뒤 만료한다. 백업 작업이 영구삭제 목록을 받아 따로 지우는 기능은 만들지 않는다.

2026-10-20 영구삭제 설계의 "앱 자동 백업 속 고객 자료 제거"는 앱이 PC에 만드는 SQLite 자동 백업에 대한 규칙이다. 회사가 관리하는 NAS 백업은 이 문서의 1년 보관 규칙을 따른다. 영구삭제 화면의 안내는 "회사 백업에는 1년간 남은 뒤 자동 삭제됩니다"로 바꾼다.

복구할 때는 격리된 위치에 먼저 내려받고, 현재 DB에서 필요한 키만 R2로 올린다. 백업 전체를 R2에 그대로 덮어쓰지 않는다. 영구삭제 목록에 있는 키는 일반 복구에서 제외한다.

## 7. 점검(대조)

주 1회(백업 작업 다음) 서버가 `report/`, `earth/` 목록과 DB를 대조한다.

| 결과                                        | 처리                                                        |
| ------------------------------------------- | ----------------------------------------------------------- |
| DB 보관 항목인데 R2에 없음 (누락)           | 경고. 백업에서 복구할 후보로 표시. 자동 처리하지 않음       |
| R2에 있는데 DB에 없음 (고아), 7일 이상 경과 | 백업 확인 조건을 만족하면 삭제                              |
| 허용되지 않은 최상위 접두사                 | 경고만 표시                                                 |
| 크기·SHA-256 메타데이터 불일치              | 경고. 사진은 정식 저장 때 기록한 `sha256` 메타데이터와 비교 |

결과는 개수·키·상태만 기록하고 사진·KML 내용이나 주소를 로그에 남기지 않는다. 설정 화면의 저장소 상태에 마지막 백업 시각, 삭제 대기 수, 누락·고아 수를 표시한다.

**구현 상태(2026-10-23)**: 사장님·마스터가 설정의 **저장소 점검**을 눌러 실행한다(`earth-assets`의 `check`). 누락·고아(7일 경과 구분)·접두사 위반을 세어 저장만 하고 아무것도 지우지 않는다. 주 1회 자동 실행, 고아 자동 삭제, 백업 시각 표시는 NAS 백업이 정해진 뒤 구현한다. 목록이 2만 개를 넘으면 일부만 확인하고 누락은 보고하지 않는다. 크기·SHA-256 메타데이터 비교는 아직 하지 않는다.

## 8. 용량

- 8GB 앱 예산은 유지한다. 삭제 완료 때 `total_bytes`를 0으로 반환한다(현행 교체 경로와 동일). 영구삭제 보고는 행을 제거하므로 함께 반환된다.
- 미완료 예약 7일 만료로 예산 누수를 막는다.
- 현재 예산은 회사 구분 없는 전체 합계다. 회사가 하나인 동안은 유지하고, 여러 회사를 받게 되면 회사별 예산으로 나눈다.

## 9. 이전 순서

1. **NAS 백업 구축**: 읽기 전용 토큰, 일일 백업, 암호화, 1년 보관 폴더를 만들고 첫 전체 백업과 복구 시험(임의 파일 1개를 격리 위치에 복원해 해시 대조)을 확인한다.
2. **백업 확인 기록**: 서버 전용 함수·토큰을 배포하고 백업 작업이 매일 기록을 남기는지 확인한다. 이 시점까지 자동 삭제는 꺼져 있다.
3. **경로 이전**: 객체 목록 표와 사업지역·시군 목록을 만들고, 업로드를 잠시 멈춘 뒤 기존 사진·KML을 새 폴더 구조로 복사해 크기·SHA-256을 확인한다. 새 경로를 쓰는 서버 함수를 배포한 뒤 이전 키를 백업 확인 후 지운다. 10/19 점검에서 사진 객체가 0개였으므로 이전량은 매우 적을 것으로 예상하지만, 실행 직전에 실제 목록을 다시 확인한다.
4. **자동 삭제 활성화**: 새 기본 분류·삭제 조건·미완료 예약 만료를 담은 후속 SQL 버전을 배포한다. 동결된 이전 배포 파일은 수정하지 않는다.
5. **기존 보류 건 처리**: 전환 이후 `blocked`로 쌓인 항목의 목록(개수·종류·키)을 먼저 보여 드리고, 확인을 받은 뒤 새 규칙으로 넘긴다.
6. **첫 점검 실행** 후 `work-reports.md`, `backend.md`, `data.md`의 보관·삭제 설명을 이 문서에 맞게 고친다.

각 단계는 운영 적용 전에 사용자 확인을 받는다. 이 문서의 승인만으로 운영 R2·SQL·NAS를 변경하지 않는다.

## 11. 검증 기준

가짜 회사와 가짜 R2(로컬 사진 저장소)로 다음을 확인한다. 실제 고객 자료로 시험하지 않는다.

1. 같은 묘지에 보고 3건을 공개하면 가장 오래된 보고의 사진만 퇴역하고, 보고 기록·청구·입금 이력은 유지된다.
2. 백업 확인 기록이 없거나 48시간보다 오래되면 어떤 파일도 삭제되지 않고 "백업 확인 대기"가 표시된다.
3. 백업 시작 이후에 저장된 파일은 다음 백업 전까지 삭제되지 않는다.
4. 공개 후 6분 안에 도착한 늦은 업로드가 파일을 되살리지 않는다. 퇴역 후 늦은 업로드는 다시 삭제된다.
5. KML 교체 시 현재 연결 버전은 남고 이전 버전의 원본·manifest·임시 파일이 지워진다. 다른 묘지가 참조하는 버전은 지우지 않는다.
6. 영구삭제 고객의 사진·KML이 R2에서 지워지고 NAS 백업에는 1년 남은 뒤 만료되며, 같은 이름·주소의 다른 고객 파일은 영향이 없다. 일반 복구 절차가 영구삭제 고객 파일을 R2로 되돌리지 않는다.
7. 묘지 지역을 바꿔도 기존 사진·KML은 예전 폴더에서 계속 보이고, 그 뒤에 올린 파일만 새 지역 폴더에 저장된다.
8. Mac·Windows·Android·iPhone에서 만든 같은 지역 이름이 R2와 NAS에서 폴더 하나로만 생긴다.
9. 검토 대기·임시 자료가 NAS 백업에 들어가지 않는다.
10. 7일 지난 미완료 예약이 해제되어 예산이 돌아오고, 기기 초안의 재시도가 새 예약으로 성공한다.
11. 대조 점검이 누락·고아·접두사 위반을 정확히 세고, 고아 파일은 7일과 백업 조건을 모두 만족할 때만 지운다.
12. R2 삭제 실패와 백업 실패를 성공으로 표시하지 않고 다음 실행에서 재시도한다.
13. 경로 이전 전후로 모든 파일의 크기·SHA-256이 같고, 앱 재설치 없이 조회·업로드가 동작한다.

## 12. 남은 확인 사항

- 사업지역·시군 목록의 기준(현재 `business_region`·`region` 값 정리 필요 여부).
- NAS 모델·QTS 버전·저장 공간과 백업 실행 위치(NAS 컨테이너 또는 사내 PC).
- 서버 전용 정리 경로의 권한 범위(구현 계획에서 결정).

## 검토 요청 파일 (2026-10-25, 4-2c-3b)

영업·관리자(요청자)가 위치가 있는 신규 등록을 "검토 요청"하면 다음 순서로 처리한다.

1. 앱이 먼저 KML·스크린샷을 서버에 올린다. 서버 함수가 `review/{workspaceId}/{요청ID}/`(original.kml, earth.jpg, manifest.json)에 쓰기 전에 크기·형식·해시를 확인한다. 올리는 임시 칸은 `staging/{workspaceId}/{요청ID}/`.
2. 올리기가 끝난 것이 확인돼야(`registration_request_files.state='ready'`) 요청이 접수된다. 요청은 예약했던 묘지 번호를 가져가고, 예약은 이때 소모된다. 파일의 묘지 번호가 예약 번호와 다르면 접수하지 않는다.
3. 어느 단계든 실패하면 요청은 보내지지 않고 입력과 PC의 KML 사본이 그대로 남는다. 같은 요청을 다시 누르면 같은 요청 번호·같은 매니페스트로 이어서 올린다.
4. 접수되면 요청자 PC의 KML 사본(Google Earth 폴더·내려받기 폴더)과 앱 작업 사본을 지운다. 요청자는 그 뒤로 자료를 볼 수 없다(서버에 요청자용 목록·내려받기 동작이 없다).
5. 키는 `stored_objects`에 `ref_kind='request'`로 예약되고, 저장소 점검은 `review/{workspaceId}/`를 함께 살핀다. 올리기가 끝난 요청 파일만 "있어야 하는 파일"이며 끝나지 않은 것은 "알려진 파일"로만 센다.
6. 승인(4-3, 2026-10-25): 마스터·부마스터의 앱이 요청의 KML·스크린샷을 `request-read`(서명된 읽기 주소)로 받아 해시를 확인하고, 기존 직접 등록과 같은 절차(준비 → 정식 묘지 폴더에 올리기 → 등록)로 저장한다. 등록 명령에 `fromRequest`가 붙으며 서버는 같은 트랜잭션에서 요청을 `approved`로 바꾸고(처리자·시각 기록) 묘지는 요청이 예약해 둔 번호를 쓴다. 한 요청은 한 번만 승인된다. 승인이 끝나면 앱이 `request-discard`로 `review/`·`staging/`의 요청 파일과 요청 파일 표를 지운다(실패해도 승인은 유지, 남은 파일은 4-5에서 정리).
7. 반려(4-4, 2026-10-25): 마스터·사장님만 한다(`delete` 권한). 대기 중인 요청만 `rejected`로 바꾸고 입력 내용·요청자 이름·예약 묘지 번호를 비운다(번호는 다시 쓰지 않는다). 고객은 만들어지지 않고 요청자에게는 알리지 않는다. 앱은 이어서 `request-discard`로 `review/`의 파일을 지운다.
8. 같은 경계 차단(4-4): 경계(Polygon 바깥 고리, 소수 6자리, 시작점·방향 무시)의 해시를 `demo_desktop.boundary_keys`에 둔다. 묘지는 `earth_links` 트리거가, 대기 중 요청은 올리기를 시작할 때(`request-begin`) 기록한다. 다른 묘지(삭제된 묘지 제외) 또는 다른 대기 요청과 같은 경계는 올리기·준비 단계에서 `duplicate-boundary`로 막는다. 파일 이름만 바꾸거나 다시 저장해도 같은 키이고, 경계를 다시 그리면 다른 키다. 비슷한 경계·같은 고객은 비교하지 않는다. 점(Point)은 검사하지 않는다. 요청의 키는 승인·반려·파일 정리 때 지운다.
9. 남은 파일 정리(4-5): 승인·반려된 요청의 파일, 요청이 오지 않은 채 2일이 지난 올리기를 `request-sweep`이 찾아(한 번에 20건) `request-discard`와 같은 절차로 지운다. 마스터·부마스터의 검토 화면이 목록을 불러올 때, 앱을 켠 뒤 처음 한 번과 그 뒤 하루에 한 번 조용히 실행한다(서버 부담을 줄이기 위해). 한 번에 20건을 다 채우면 이어서 바로 다음 묶음을, 실패하면 1시간 뒤에 다시 시도한다.
