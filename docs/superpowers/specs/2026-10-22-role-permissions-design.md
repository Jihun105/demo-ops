# 계정 권한 재설계 (마스터·부마스터·관리자·영업·일반 작업자)

상태: 2026-10-22 사용자 답변을 반영한 5차 설계(모든 삭제는 마스터만, 작업 배정은 관리자). 2단계 구현 완료(개발 서버에서 확인), 운영 반영은 2-6 대기. 4장 영업 등록 검토 흐름은 4단계에서 진행한다. 휴대폰 화면은 별도 설계에서 다룬다(6장).

## 1. 사용자 요구 (2026-10-22)

- **마스터**: 전체 다 가능.
- **부마스터(신설)**: 고객 정보 수정 가능. 영업·관리자가 올린 신규 등록을 검토·승인한다. **삭제 불가**(2026-10-22 확정).
- **관리자(사무실 직원)**: 데스크톱 사용. 이전 고객 정보 조회, 청구·입금 조회·입력, 기존 고객 영업 전화(통화 중 요구사항·특이사항 수정 포함). 그 밖의 고객 정보 수정·삭제·직원 계정 관리는 불가. 신규 등록은 검토 요청으로만.
- **신규 등록은 무조건 마스터·부마스터의 승인을 거친다**(2026-10-22 확정). 마스터·부마스터가 직접 등록하는 것은 본인 승인으로 보고 바로 저장한다.
- **작업 배정·경로 짜기는 관리자가 한다**(2026-10-22 확정). 관리자보다 위인 마스터·부마스터도 할 수 있다. 배정·순서를 바꾸고 다시 저장하는 것은 되지만, 작업·경로를 지우는 것은 삭제로 보아 마스터만 한다.
- **모든 삭제는 마스터만** 한다(2026-10-22 확정). 삭제는 고객 숨김·영구삭제·올해 작업 삭제·작업 경로 삭제·입금 기록 삭제를 모두 포함한다.
- **직원 계정 관리는 마스터·부마스터만** 한다. 관리자·영업·일반 작업자는 계정 관리 권한이 없다(2026-10-22 확정).
- **영업**: 데스크톱에서 신규 고객 입력만 한다. 이전 고객은 볼 수 없고, 저장한 순간부터 자기가 넣은 고객도 볼 수 없다. 삭제 불가.
  - 저장을 누르면 바로 고객 DB에 들어가지 않는다. **마스터·부마스터가 한 번 검토한 뒤** 고객 DB에 저장된다.
- **일반 작업자**: 휴대폰 사용. 묘지 위치·특이사항·기수·면적·고객 요구사항은 보기만 한다. 작업 목록·순서와 배정 작업 사진 등록은 유지한다. 자세한 내용은 휴대폰 설계 때 다시 정한다.

  - 구글 어스 위치 원본 열기(저장·가져오기는 불가)
  - 자료 정리 상태(파일 분류는 마스터만)
- **영업 데스크톱 로그인 (4단계 전 임시):** 신규 등록 화면만 보인다. 고객 자료는 받지 않는다(PC 프로그램이 인증 외 모든 요청을 거절). 입력은 해 볼 수 있지만 등록·거절 버튼은 승인 대기 흐름이 생길 때까지 잠근다.

## 4. 영업 신규 등록 검토 흐름

### 4.1 영업·관리자

관리자도 신규 등록은 같은 검토 요청으로 올린다. 관리자는 기존 고객을 볼 수 있으므로 메뉴가 줄지는 않고, 등록 화면의 저장 버튼만 **검토 요청**으로 바뀐다. 아래 1~3은 영업 기준이다.

1. 데스크톱 로그인 → **신규 등록 화면만** 열린다. 고객 목록·검색·지도·작업·청구 메뉴는 없다. 회사 고객 자료를 PC로 내려받지 않는다.
2. 이름, 전화번호, 묘지 주소, 기수, 면적, 요구사항, 특이사항, 위치(Google Earth KML)를 입력한다.
3. **검토 요청**을 누르면 서버의 등록 요청함에 들어가고 입력 창이 비워진다. 화면에는 "검토 요청 완료"만 표시하고, 넣은 내용은 다시 볼 수 없다.

### 4.2 마스터·부마스터: 등록 검토 화면 (신설)

데스크톱에 **등록 검토** 화면을 따로 둔다. 마스터·부마스터에게만 보인다.

- 메뉴에 대기 건수 표시(예: 등록 검토 3). 새 요청이 오면 열려 있는 데스크톱에 바로 반영한다. (2026-10-25 결정: 서버 부담을 줄이려고 자동 갱신은 하지 않고, 앱을 켤 때·화면에 들어갈 때·새로고침을 누를 때만 불러온다. 화면은 고객 관리 안의 탭이 아니라 사이드바의 독립 메뉴다. 2026-10-26: "검토"를 누르면 팝업에 보낸 내용·위치·스크린샷(누르면 크게)이 뜨고, 팝업에서 바로 승인·반려한다. "수정"을 누르면 팝업 안의 입력 칸에서 고친 뒤 승인한다(신규 등록 화면으로 넘어가지 않는다).)
- **목록**: 접수 시각, 올린 영업 직원, 고객 이름, 묘지 주소, 위치(KML) 유무. 오래된 순. 중복 의심 표시는 두지 않는다(2026-10-22 사용자 결정).
- **상세**: 입력 내용 전체와 위치 지도. 비슷한 기존 고객 비교는 이번 단계에서 하지 않는다(2026-10-22 사용자 결정).
- 필요하면 고쳐서 **승인** → 이때 실제 고객·묘지가 만들어진다(기존 `register` 사용). 기록: 입력자(영업), 승인자, 승인 시각.
- **반려** → **마스터만** 할 수 있다(2026-10-22 사용자 결정, 부마스터는 승인만). 사유를 남기고 고객 DB에는 넣지 않으며, 즉시 KML·이미지를 삭제한다.
- 같은 요청을 두 사람이 동시에 처리하지 못하게 요청 단위로 잠근다.

#### 같은 경계 차단

2026-10-22 사용자 결정으로 "경고만"에서 **차단**으로 바꿨다. 자세한 규칙은 [KML 위치 설계](2026-10-22-kml-location-design.md) 4.3.

- 요청의 묘지 경계가 DB의 다른 묘지 경계나 처리 중인 다른 요청과 **좌표가 완전히 같으면** 검토 요청과 승인을 막는다(예: 328번 경계를 띄운 채 이름만 412로 바꿔 내보낸 경우). 파일 이름이 다르면 파일 지문은 달라지므로 좌표로 비교한다.
- 새로 다시 그린 경계는 점이 조금씩 달라 해당되지 않는다. 그 밖의 중복 표시·비슷한 고객 비교는 하지 않는다(기존 결정 유지).
- 위치 없이 올라온 요청은 검사하지 않는다. 영구삭제된 묘지·반려된 요청은 대상에서 뺀다.

### 4.3 서버

- 새 표 `demo_desktop.registration_requests`: 요청 ID, 회사, 올린 사람, 올린 시각, 입력 내용(jsonb), 예약 묘지 번호, 상태(`pending`/`approved`/`rejected`), 처리자, 처리 시각, 반려 사유, 승인으로 생긴 고객 ID.
- 영업은 이 표에 **넣기만** 할 수 있고 조회 함수가 없다. 고객 DB·공유 목록·휴대폰 자료에는 승인 전까지 나타나지 않는다.
- **반려한 요청은 보관하지 않는다**(2026-10-22 사용자 결정). 반려하는 순간 요청 내용(이름·전화·주소 등)과 KML·이미지를 모두 지운다. 같은 요청이 통신 재시도로 다시 들어와 되살아나지 않도록 **요청 번호와 '반려됨' 표시만** 남긴다(개인정보 없음).
- 반려 사실을 올린 사람에게 알리지 않는다(2026-10-22 사용자 결정).
- 오래 처리하지 않은 요청은 자동으로 지우지 않는다. 마스터·부마스터 화면의 대기 건수로 관리한다.
- 등록 요청함은 DB에 등록된 자료가 아니므로 **서버 DB 백업에서 제외**한다(2026-10-22 사용자 결정, 표 데이터 제외). 서버 사고 시 검토 대기 건은 다시 올린다.

### 4.4 위치(KML)와의 연결

[KML 위치 설계](2026-10-22-kml-location-design.md)는 신규 등록 때 **구글 어스로 찾기**를 누르면 묘지 번호를 예약하고 24시간 뒤 자동 취소한다. 영업 등록은 검토를 기다리므로:

- 예약 번호와 KML은 **요청이 처리될 때까지** 유지한다(24시간 자동 취소에서 제외).
- 승인하면 그 번호로 묘지와 위치가 함께 저장된다. 반려하면 예약을 버리고 R2의 KML·이미지를 지운다([R2 보관 설계](2026-10-22-r2-storage-lifecycle-design.md)의 삭제 규칙 적용).

### 4.5 위치 수정 메모

관리자는 기존 고객의 위치를 고치지 않는다. 영업 통화 중 위치가 이상하면 **위치 수정 메모**를 남기고 마스터·부마스터가 처리한다(2026-10-22 사용자 결정, [KML 위치 설계](2026-10-22-kml-location-design.md) 4.4).

- 서버 표(예: `demo_desktop.location_notes`): 묘지, 메모, 남긴 사람·시각, 상태(열림/처리 완료/수정 불필요), 처리자·시각. 묘지마다 열린 메모는 하나다.
- 새 위치가 저장되면 그 묘지의 열린 메모를 자동으로 처리 완료로 바꾼다.
- 고객 영구삭제 때 함께 지운다.

## 5. 서버에서 바꿀 곳 (조사 결과)

지금은 데스크톱 권한이 "사장님 또는 마스터"로 고정돼 있다. 여러 곳에 흩어진 역할 목록을 **기능 단위 판정 함수 하나**(예: `demo_desktop.allow(workspace, 기능)`)로 모은다.

- `database/cloud/access.sql`: 역할 check 제약, `demo_can_manage`, `demo_desktop_access`(현재 owner·master만)
- `database/cloud/desktop/core.sql`: `assert_actor`, `lock_actor`(현재 회원 중 `master`만 통과) → 명령별 허용 판정으로 교체
