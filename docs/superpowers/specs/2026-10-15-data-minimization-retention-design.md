# 서버 전송 최소화와 고객 삭제·회계 기록 보존 설계

상태: 2026-10-15 사용자가 방향과 작성된 설계를 승인했다. 원래 13개 개선 목록의 **8번**에 해당한다. 구현 계획(완료 후 문서 정리로 삭제)을 작성해 검토를 기다리는 단계이며 제품 코드·운영 SQL·실제 자료는 아직 변경하지 않았다.

## 목적과 사용자 합의

사용자는 필요한 고객 정보만 서버에 보내고, 고객을 영구 삭제해도 과거 청구·입금 기록을 확인할 수 있는 운영 방식을 선택했다. 불필요한 개인정보는 정리하며, 법적으로 보존할 거래 증빙은 일반 영업 자료와 분리한다. 영구 삭제는 이름만 화면에서 가리는 기능으로 설명하지 않는다.

성공 기준은 기존 업무·금액·식별번호를 유지하면서 서버의 불필요한 필드, 과거 사본의 중복 개인정보, 삭제 고객의 일상적인 재노출을 줄이는 것이다. 개인정보 전체를 무조건 5년 또는 10년 보관한다는 규칙은 만들지 않는다. 이미 없어진 원본이나 접속하지 않는 기기의 사본까지 지웠다고 표시하지 않는다.

7번의 여러 PC 공동 작업은 소스 구현·검증을 마쳤지만 운영 SQL/함수 적용·기준 DB 이전·실제 설치본 검증은 남아 있다. 8번이 끝나도 이 운영 전환이 자동 완료된 것으로 취급하지 않는다. 기존 `20261014-schema-control`과 `20261014-multi-desktop` 동결 파일은 수정하지 않고 후속 배포로 연결한다.

| 방식                                 | 장점                                          | 문제                                                                                  |

하나의 서버 DB 안에서 비공개 테이블과 목적별 API로 분리한다. 별도 서버, 외부 개인정보 관리 서비스, 새 직원 역할은 추가하지 않는다. 기존 사장님·마스터·현장 관리자·일반 작업자의 역할 체계를 유지한다.

## 1. 서버 전송·반환 계약

전송 경계의 공용 DTO 검증기를 사용하고 서버에서도 같은 허용 목록을 검증한다. 원본 행의 spread나 `data` 전체 반환으로 네트워크 JSON을 만들지 않는다. 로컬 검증·백업에서 전체 행을 읽는 것 자체를 금지하지는 않는다.

| 자료                  | 전송·반환할 업무 필드                                                                                                                      |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 고객                  | ID, 이름, 정규화 전화번호와 입력 표기, 번호 확인 상태, 요구사항, 특이사항, 등록/거절 상태, 보관·생성 시각, 편집 버전                       |
| 묘지                  | ID, 고객 ID, 주소, 구분/순서, 계약연도, 기수, 평수, 업무 메모, 활성/보관 상태, 생성 시각, 편집 버전                                        |
| 연도별 청구 기준 금액 | ID, 묘지 ID, 연도, 금액, 종류, 관련 날짜·방법·업무 메모, 정해진 출처 코드                                                                  |
| 연간 작업             | 기존 작업 ID/키, 고객·묘지 ID, 서비스 연도, 진행 상태, 특이사항·기한, 삭제 상태·버전                                                       |
| 위치·Earth            | 묘지/버전 ID, 주소에 결합한 허용 좌표·출처·검증 정보, 선택 geometry, 파일명·해시·크기와 업로드 상태. 로컬 절대경로·인증 토큰·서명 URL 제외 |
| 동기화·배정           | 회사·계정 범위, 순번·세대·버전·요청 ID, 배정 상태와 필요한 기술 메타데이터. 영업 토큰은 기존처럼 메인에만 보관                             |

`extra_json`, `source_row`, 원본 엑셀 파일/시트/로컬 경로와 임의 추가 컬럼은 일반 고객 전송에서 제외한다. 현재 소비자가 쓰는 `gubun`, 금액 메모, 계약연도 등은 단순히 안 보이는 컬럼이라는 이유로 지우지 않는다. 새로 발견되는 미지원 컬럼은 자동 전송하거나 원본에서 삭제하지 않고 이전을 중단해 검토하도록 한다. 알려진 로컬 전용 컬럼의 제외는 이전 검토의 항목·개수에 표시한다.

기존 로컬 원본과 검증 백업은 유지한다. 원본 전체의 로컬 checksum과 실제 전송 JSON의 checksum을 별도로 계산·보관한다. 서버는 전송한 정확한 JSON/checksum을 검증하며, 보내지 않은 원본 전체를 검증했다고 주장하지 않는다. 두 checksum과 안정적인 이전 요청 ID로 응답 유실을 복구한다. 고객/묘지/금액/작업/이벤트 ID와 고수위는 바꾸지 않는다.

직원 조회는 기존의 서버 필드 제한을 유지한다. 일반 작업자에게 고객명을 새로 제공하거나 직원에게 금액·청구·입금·고객 메모·원본 KML을 새로 제공하지 않는다. 기존 현장 연락 전화와 작업 주소는 유지하고 회사 전체 조회 범위를 임의로 현장 배정 단위로 바꾸지 않는다. 회계 보관함은 직원 catalog나 지도 snapshot에 합치지 않는다.

## 2. 회계 보관과 조회

일반 고객·영업 원본과 분리한 비공개 회계 보관 영역을 만든다. 사장님과 활성 마스터만 회사·실제 auth 세션을 확인한 목적별 API를 이용한다. 앱 역할의 원본 테이블 직접 읽기/수정은 허용하지 않고, 현장 관리자·작업자에게 회계 보관 권한을 추가하지 않는다.

보존 대상은 다음과 같다.

- 연도별 청구 기준 금액: 기존 ID·묘지/고객 참조·연도·종류·금액·출처 코드와 필요한 거래 메모. 실제 입금으로 표시하지 않는다.
- 청구·발송·입금·취소: 원래 이벤트 ID, claim/payment/attempt/report/task 참조, 시각·금액·통화/계산 의미·발송/취소 상태를 보존한다. 기존 금액을 다시 추정하거나 이름·주소로 새 연결을 만들지 않는다.
- 은행 수신 증빙: 기존 receipt/fingerprint/payment 연결, 입금자·입금/수신 시각과 실제 필요한 문자 발췌를 기록별 보존 대상으로 분류한다.
- 거래 입증에 필요한 계약 상대 식별·발송 본문 등은 증빙으로 분류한 범위에서 별도 보관한다. 고객 행·자유 메모·전체 KML/사진을 편의상 통째로 회계 보관함에 복사하지 않는다.

기존 청구·입금 화면에서 삭제 고객의 금액과 미수 상태를 계속 확인한다. 기본 요약은 `삭제 고객 · 기록번호`와 금액·시각·처리 상태를 사용하고, 보관한 상대 식별이나 원문은 별도의 증빙 조회에서만 가져온다. 조회자·시각·증빙 ID를 기록하되 조회 로그에 원문을 중복 복사하지 않는다. ID를 남기는 것을 법적인 익명화라고 설명하지 않는다.

원본 증빙의 ID·내용·해시를 보존하고, 일상 조회용 제한된 표현과 구분한다. 제한된 표현은 별도 버전의 자료형으로 검증한다. 구형 이벤트 검증을 통과시키기 위해 가짜 전화번호·주소·입금자 값을 채우지 않는다. 영구 삭제 고객에게 기존 문자·완료 문자 재발송이나 새 영업 청구를 자동으로 실행하지 않는다.

미수금·늦게 들어온 입금·입금 취소도 계속 관리해야 한다. 은행 판정은 회계 내부의 동일 ID·엄격한 기존 조건으로 처리하고 중복 수신/취소의 합계가 바뀌지 않게 한다. 보관 고객을 일반 영업 목록으로 되살리지 않는다. 명확한 연결이 없으면 기존처럼 자동 반영하지 않고 확인 대상으로 남긴다.

## 3. 고객 보관·영구 삭제의 순서

일반 삭제 목록은 복원용 보관 상태로 유지한다. 사용자에게 일반 보관과 개인정보 파기의 차이를 안내한다. 등록 거절은 별도 업무 상태이며 거절만으로 파기된 것으로 취급하지 않는다. 거래 없는 거절 고객에게 회계 보존 사유를 자동으로 붙이지 않는다. 재연락 방지용 최소 정보가 필요하다면 목적·범위·기간을 별도로 설정한다.

영구 삭제는 기존 회사 잠금, 권한, 영업 점유, 편집 버전과 안정적인 요청 ID를 재사용하여 다음 순서로 처리한다.

1. 대상과 관계를 고정하고 연도별 금액·청구/입금/은행 증빙의 개수·ID·금액 합계·원문 해시를 확인한다.
2. 보존 대상은 회계 영역에 중복 없이 보관하고 보존 결과가 원본과 일치하는지 검사한다. 보존에 실패하면 고객 삭제도 롤백한다.
3. 일반 고객·묘지·작업·위치와 불필요한 연락처·자유 메모의 업무 사본을 제거하고 조회 projection을 갱신한다. 회계 보관 기록은 고객 FK의 cascade 삭제 대상이 아니어야 한다.
4. 과거 고객/작업 동기화 값, 저장 결과 안의 위치/파일명, Earth 후보/메타데이터, 관련 캐시를 정리할 작업을 같은 트랜잭션에 기록한다. 증빙으로 보존한 부분은 일반 이력에서 분리한다.
5. 금융 원본/제한된 동기화 표현을 분리하고 클라이언트의 전송·읽기 세대를 갱신한다. 과거값을 다시 합쳐 개인정보가 복구되지 않게 한다.
6. R2와 기기 사본의 정리는 커밋 이후 재시도한다. DB 삭제가 성공했는데 파일 정리가 대기 중이면 성공한 DB 작업을 실패로 되돌려 표시하지 않는다.

금액 합계·원본 이벤트 ID·입금 취소·중복 방지 결과는 삭제 전후 같아야 한다. 미연결 묘지 삭제도 그 묘지의 연도별 금액과 관련 증빙을 같은 원칙으로 보존한다. 이름/주소가 같다는 이유로 다른 고객의 증빙이나 파일을 함께 처리하지 않는다.

신규 보존 영역의 생성만으로 기존 고객 전원을 복사하지 않는다. 회사 전환과 실제 영구 삭제에서 목적에 맞게 이전하며, 사전 검토는 항목·개수·합계·해시만 보고한다. 초기 전환도 중간 실패와 같은 요청 재실행에 안전해야 한다.

## 4. 보존 기간과 파기 정책

확인한 법령은 개인정보가 불필요해진 경우의 파기, 법정 보존 개인정보의 분리 관리, 세무/상업 기록 종류별 보존을 구분한다. 이 설계가 회사별 기록의 법적 분류나 파기 승인을 자동으로 대신하지 않는다.

정책은 기록 종류, 보존 목적/근거, 보존할 필드, 기산 사건/날짜, 기간, 확인자/확인일, 분쟁·미수 등 보류 사유를 포함한다. 기술적으로 실행할 수 있는 확정된 정책만 자동 처리한다.

- 처음 배포할 때 회계 증빙·복원용 보관·거절 고객·백업의 자동 파기 정책은 비활성이다. 임의의 30일/5년/10년을 하드코딩하지 않는다.
- 회계 기간/기산일/보존 근거가 미확정인 기록은 `보존 기준 확인 필요`로 제한 보관하고 자동 파기하지 않는다. 회사가 적용 기준을 확인하기 전 법정 보존·파기 완료로 표시하지 않는다.
- 확정 정책의 기산일이 없거나 자료가 미분류면 파기하지 않고 원인을 표시한다. 미수금·명시적 분쟁 보류는 근거·확인자·상태를 기록하고 해제 전까지 자동 파기에서 제외한다.
- 영구 삭제한 고객의 불필요한 업무 사본 정리는 회계 보존기간과 별개로 바로 요청한다. 회계 보존을 이유로 전체 고객 프로필을 영업 DB에 남기지 않는다.
- 순수 기술 이력은 변경자·시각·동작·대상 ID·결과·요청 ID 중심으로 남기고 개인정보 원문을 무기한 복제하지 않는다. 계정 ID/대상 ID도 접근 제한 대상이다.
- 수동 파기도 미리보기·버전·권한·보류 상태를 검증한다. 회사 운영 기준이 없는 상태에서 실제 기존 자료를 일괄 삭제하는 버튼은 제공하지 않는다.

법령 근거(2026-10-15 확인):

- [개인정보 보호법 제21조](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0021&lsiSeq=283839&urlMode=lsScJoRltInfoR): 불필요한 개인정보의 파기와 다른 법령에 따른 보존 자료의 분리 관리.
- [국세기본법 제85조의3](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1008304643): 일반 세무 장부·증빙은 해당 법정신고기한 이후 원칙적 5년이며 예외가 있다. 모든 고객 메모의 보존 근거로 일반화하지 않는다.
- [상법 제33조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0033&lsiSeq=284143&urlMode=lsScJoRltInfoR): 상업장부·중요서류와 전표의 기간을 구분하며 장부의 기산 기준을 정한다. 회사의 기록별 분류·보존 기간 확정은 운영 적용 전 확인 사항이다.

## 5. 여러 PC·모바일·구버전 전환

회사별 개인정보 처리 세대와 제한된 회계 조회 형식의 버전을 서버가 발급한다. 개인정보 정리를 포함한 동기화 세대 변경 시 기존 증분 이력을 그대로 되돌려 읽지 않고 최신 정리된 기준을 받는다. 기준 생성과 세대 변경은 한 회사 잠금에서 처리하여 중간 거래를 놓치지 않는다.

새 클라이언트는 과거 원문을 포함하는 로컬 이벤트와 서버의 제한된 표현을 무조건 합치지 않는다. 확인된 새 세대의 서버 기준으로 교체하되 미전송/결과 미확인 거래를 먼저 같은 요청·이벤트 ID로 대조한다. 삭제 대상의 초안·요청 원문은 재사용하지 않고, 이미 확정된 거래는 보존 기록의 결과로 확인한다. 결과 조회를 못하면 관련 재전송/기능을 잠그고 원인과 정리 대기를 표시한다.

기존 `demo_events`/`demo_sync_changes`의 raw 읽기·쓰기, 과거 전체 catalog 게시와 새 제한 조회를 우회하는 경로를 회사 전환 시 서버에서 차단한다. 정상 클라이언트의 신규 금융 이벤트는 검증된 경로로만 받는다. 금액 계산·은행 대조가 읽는 내부 금융 원본과 일반 앱에 전송하는 표현을 분리한다. 구버전에는 업데이트가 필요하다는 오류를 반환하고 원문으로 fallback하지 않는다. 아직 전환하지 않은 회사는 기존 동작을 유지한다.

최신 기기는 다음 온라인 확인에서 해당 고객의 조회 캐시·모바일 IndexedDB/업무 저장소·초안·요청 저널·보고 캐시·관리 원본 사본을 정리한다. 원본 해시가 다른 파일이나 다른 묘지가 참조하는 공용 원본은 지우지 않는다. 프로그램 관리 밖으로 수동 내보낸 파일은 자동 원격 삭제하지 않는다.

오프라인 기기의 사본을 즉시 삭제할 수 있다고 약속하지 않는다. 서버 정리, 확인한 기기의 정리, 알려진 미접속 기기의 확인 대기를 구분한다. 구버전/미접속 기기는 다음 사용 전에 온라인 권한·버전·정리 확인을 요구한다. 기기 확인 기록에는 설치 식별자와 필요한 버전/상태만 사용하고 하드웨어 고유번호를 새로 수집하지 않는다.

## 6. R2·백업·복구

R2 원본·사진·manifest와 DB의 후보·폐기 메타데이터도 고객 참조와 증빙 분류로 다룬다. 회계 증빙으로 분류한 첨부를 일반 작업 사진과 구별하고, 보존하지 않을 객체는 현재 참조와 다른 고객/묘지 참조를 확인한 정리 작업으로 삭제한다. 파일 삭제 실패/늦은 업로드는 재시도하고 새로 교체된 원본을 지우지 않는다. 파일명 자체의 개인정보도 검토하며 객체 접근 차단과 바이트 삭제 완료를 구분한다.

기존 고객/이전 백업을 무조건 삭제하거나 삭제 전 전체 원문 백업을 매번 추가해 파기 목적을 무력화하지 않는다. 백업은 운영 자료와 별도의 접근·기간 정책으로 관리한다. 현재의 30개 보관 개수만으로 기간 관리가 끝났다고 표시하지 않는다.

파기 대상이 든 백업은 해당 확정 정책에 따른 교체/만료 작업과 상태를 기록한다. 분리 보관 중에는 일반 앱 조회·자동 복원에 쓰지 않는다. 회사가 관리하는 외장/서버 백업도 운영 목록에 포함하고 관리 밖 사본은 정리 완료라고 표시하지 않는다. 복원은 격리된 위치에서 최신 삭제/보존 기준을 다시 적용하고, 오래된 DB를 새 서버에 전체 게시하지 않는다. 삭제 방지용 최소 식별 기록은 일반 고객 원문과 별도로 보관하여 복원 후 재적용하며 그 자체도 접근 제한·정책 대상이다.

회계 보관 원본의 복구 가능성을 별도 백업/복구 시험으로 확인한다. 현재 미완료인 개선 2번의 맥 밖 암호화 백업 위치 선택은 이 설계만으로 완료되지 않는다. GitHub 소스 백업은 실제 업무 데이터 백업과 구분하고 기존 외부 전송 승인 대기를 유지한다.

## 7. 화면과 처리 상태

새 개인정보 관리 제품이나 대규모 화면 개편은 하지 않는다. 기존 고객 영구 삭제 안내, 청구·입금 조회, 설정에 필요한 범위만 추가한다.

- 영구 삭제 안내에 제거할 업무 자료와 남길 회계 증빙을 구분하고 사전 개수·합계만 표시한다.
- 청구·입금 화면은 삭제 고객의 금액을 유지하고 제한된 증빙 조회를 제공한다. 필요 없는 원문을 검색·목록·전체 동기화에 계속 포함하지 않는다.
- 설정에서 기록 종류별 정책의 확정/미확정/활성 상태와 정리 대기를 확인한다. 분류·기산일·보류를 검증한 후 확정한다.
- 상태는 `업무 자료 제거`, `회계 증빙 보존`, `서버 사본 정리 대기/완료`, `기기 확인 대기`, `백업 정책에 따른 정리 대기`를 별개로 표시한다. 모든 사본에 대한 완전 파기나 법 준수 완료를 단일 성공 메시지로 표시하지 않는다.
- 단순 ID 표시는 익명화가 아니고, 구버전이나 미접속 기기에는 제한이 있다는 점을 필요한 화면에서 설명한다.

## 8. 단계와 검증 기준

전체 개선 8번 안에서 아래 순서로 나눠 구현한다. 내부 단계 완료를 전체 8번 완료로 보고하지 않는다.

1. **전송 항목 제한**: 공용 DTO, 서버 입력/반환 검증, 원본/전송 checksum 분리와 이전·기존 업무 호환.
2. **회계 보존과 삭제 결합**: 비공개 증빙 원본/제한 조회, 기존 합계·ID 유지, 은행 판정·취소·미수 관리, 삭제 실패의 원자적 롤백.
3. **이력·사본 정리와 전환**: 세대/읽기 경로/구버전 차단, 기기 캐시·초안·저널, R2와 백업/복원 정리, 확정 정책의 실행.
4. **운영 검증**: 후속 동결 배포·원본/전송 항목 검토·정책 확정과 소유자 확인, 설치 기기 업데이트/회계 합계 대조 후 활성화.

검증은 다음 위험에 집중하고 단순 문구/표시 변경마다 전체 테스트를 반복하지 않는다.

- 가짜 추가 컬럼·`extra_json`·원본 경로가 전송 JSON과 직원 응답에 들어가지 않고 원본 로컬 바이트/ID는 유지된다.
- 삭제 전후 청구 기준·실제 입금·입금 취소·부분/중복 입금의 ID와 합계가 같다. 보존 실패 시 삭제도 취소된다.
- 같은 삭제 요청의 응답 유실/재시도·동시 PC 수정·영업 점유·같은 이름의 다른 고객·미연결 묘지에 안전하다.
- 이전 고객명/전화/주소/메모가 일반 snapshot·과거 증분 조회·기본 회계 요약·직원 API·저장 결과 재실행에서 재노출되지 않는다. 원문 증빙은 허용된 목적별 API에서만 나온다.
- 새 세대가 오래된 로컬 원문과 합쳐지거나 미전송 금융 이벤트가 사라지지 않는다. 구버전 raw 경로가 차단되고 새 세대 수신 실패를 완료로 기록하지 않는다.
- 다른 회사·다른 역할·로그아웃/비활성화·세션 변경을 서버가 재검사한다. 개인정보 원문이 오류/로그/검증 산출물에 나오지 않는다.
- 확정되지 않은 기간, 기산일 누락, 미수/분쟁 보류는 자동 파기로 넘어가지 않는다. 확정 정책만 경계 날짜와 함께 시험한다.
- R2 실패·늦은 업로드·공용 해시·오프라인 기기·백업 만료 전·오래된 백업 복원에서 데이터가 재생성되지 않고 대기 상태가 정확하다.
- 이전 두 동결 파일의 바이트는 유지하고 새 설치·업그레이드·동일 버전 재실행·변조 차단을 후속 배포에서 검증한다.

실제 고객 행을 시험 자료로 사용하지 않는다. 운영 정책의 기록별 근거/기산일/기간 확인, 외부 백업 위치, 서버 전환과 설치 기기 검증은 소스 테스트와 별도로 완료 상태를 기록한다. 이 문서 승인만으로 실제 기존 자료의 일괄 파기나 GitHub 외부 전송을 실행하지 않는다.
