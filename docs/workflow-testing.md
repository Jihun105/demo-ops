# 과천 20건 작업 순서·공동 배정 테스트

2026-10-19 테스트 정리 완료: 과천 테스트 앱과 전용 Docker 서버·볼륨, 가상 고객·묘지·시트·배정·사진 보고, 기기 로그인과 캡처 파일을 삭제했다. 아래는 필요할 때 테스트 환경을 다시 만드는 절차다. 운영 자료와 기존 `demo-local-test` 개발 환경은 유지했다.

기존 고객 DB의 묘지 327곳을 주소의 시·군으로 집계했을 때 경기도의 안양·의왕·과천은 없었다. 이번 샘플은 **과천**으로 정했다. 고객 20명과 묘지라는 설정은 가상이고, 전화번호는 비워두었다. 위치는 [과천시 공식 위치 자료](https://www.gccity.go.kr/dept/snowBox/list.do?mId=0707000000)에 주소와 좌표가 함께 공개된 실제 주소 20곳이다. 예: 경기도 과천시 관문동 72-27, 중앙동 73, 중앙동 57. 실제 묘지로 확인한 장소는 아니다. 공식 주소·좌표 쌍으로 테스트 KML을 만들고 기존 좌표 저장 방식으로 연결했다.

운영 DB, 운영 Supabase, 기존 앱의 회사 설정과 `.env`는 바꾸지 않는다. 테스트 회사의 서버는 이 맥의 `127.0.0.1:55321`, Studio는 `127.0.0.1:55323`이고, 휴대폰 화면은 `127.0.0.1:55331`이다. 고객 DB와 앱 설정·휴대폰 로그인은 `artifacts/workflow-test/` 안에서 따로 보관한다. 기존 로컬 연습 서버 `demo-local-test`도 유지한다.

## 실행 및 로그인

```sh
npm run workflow:test
```

실행 후 PC 창 위에 **테스트 회사 · 과천 가상 자료 20건** 표시가 있어야 한다. 새 환경에서는 아래 계정으로 로그인한다. 환경이 남아 있다면 다시 실행할 때 수정한 테스트 자료를 보존한다. 최초 구성은 로컬 Docker 네트워크 `demo-local-test-loopback`을 사용하며 새 DB의 기본 함수·테이블 권한을 동결 기준과 맞춘 뒤 설치한다. 이미 존재하는 DB를 자동 초기화하지 않는다.

| 화면            | 계정                             |
| --------------- | -------------------------------- |
| PC 사장님       | `route-owner@demo.local.invalid` |
| 휴대폰 작업자 1 | `worker01`                       |
| 휴대폰 작업자 2 | `worker02`                       |

공통 **가상 계정 비밀번호**: `Demo-workflow-test-123!`

이 계정은 이 맥의 테스트 서버에만 존재한다. 초기 상태는 고객·KML 각 20개, 올해 영업 저장·진행 작업·순서 시트·배정은 0건이다. 전년도 기준 금액만 있고 청구·입금 이력은 없다.

## 순서대로 따라 하기

1. PC **작업 관리 → 영업 확인 → 지역 → 서부 → 과천**을 선택한다. `[테스트] 과천 고객01`부터 20명이 보여야 한다.
2. 전화 결과를 **진행**으로 선택하고 올해 금액 등을 입력한 뒤 **저장**을 누른다. 다음 고객으로 이동하므로 20명 모두 반복한다. 일부를 미진행으로 두면 다음 작업 목록과 계산에서 그 고객이 제외되는지도 확인할 수 있다.
3. **작업 관리** 탭에서 과천·진행 필터를 선택한다. 모두 진행으로 저장했다면 20곳이어야 한다.
4. **작업 순서 설정**에서 과천을 선택한다. **선택 지역 지도 보기**를 열어 핀 20개를 확인하고 시작할 핀을 더블클릭한다. 목록에서 시작 묘지를 고를 수도 있다.
5. **순서 만들기**를 누른다. 실제 카카오 API로 지점 사이의 이동시간을 계산한다. 완료될 때까지 진행 상태를 확인한다. 기존 KML 좌표를 사용하며 가상 주소를 지오코딩하지 않는다.
6. **작업 확인 → 과천 시트**에서 선택한 시작점이 1번인지, 20곳이 중복·누락 없이 표시되는지 확인한다. 순서를 만들기 전에는 자동 지역 시트가 없어야 한다. **전체 순서 지도**를 열어 구글 지도에 표와 같은 1~20번 핀과 화살표 연결선이 표시되는지 확인한다. 핀을 누르면 해당 고객·주소가 표시되고 전체 보기로 모든 위치를 다시 맞출 수 있다.
7. **작업 분배**에서 과천 시트와 **테스트 작업자 1·2**를 모두 체크하고 **선택 시트 공동 배정**을 누른다.
8. 휴대폰 창의 **배정 작업 → 새로고침**에서 과천 시트와 PC의 방문 순서가 같아야 한다. 설정에서 로그아웃한 뒤 `worker02`로 로그인해 같은 시트가 보이는지 확인한다.
9. 배정한 상태에서 PC 작업 확인의 5번 행을 더블클릭해 **2번**으로 옮긴다. 기존 2~4번이 3~5번으로 밀리고 담당자는 유지되어야 한다. 휴대폰에서 새로고침 후 같은 순서인지 확인한다. 전체 순서 지도에서 현재 2번 핀을 더블클릭해 **5번**으로 옮기면 원래 순서로 돌아와야 하며, 열린 지도와 휴대폰 순서도 함께 바뀌어야 한다.
10. PC에서 **배정 해제** 후 휴대폰을 새로고침하면 시트가 사라져야 한다. 다시 배정하거나 담당자 한 명으로 변경하는 것도 확인한다.
11. 시작점을 바꿔 같은 시트를 다시 계산하면 기존 배정에는 **재배정 필요**가 표시되어야 한다. 새 시트를 배정하면 새 순서로 확인할 수 있다.

## 파일과 검증 범위

- `artifacts/workflow-test/과천-테스트-20.db`: 직접 테스트하는 별도 고객 DB
- `artifacts/workflow-test/과천-가상고객-20.csv`: 가상 고객·주소·좌표 목록
- `artifacts/workflow-test/과천-가상묘지-20.kml`: 지도 핀 20개
- `artifacts/workflow-test/screenshots/`: 실제 로그인 후 PC·휴대폰 화면
- `artifacts/workflow-test/verification.json`: 별도 자동점검 회사에서 실제 로그인/API로 확인한 20건·두 계정 공동 배정·순서 보존·해제 결과

```sh
npm run workflow:verify
```

자동점검은 직접 테스트할 회사와 다른 가상 회사를 사용한다. 주소 20곳 사이의 380개 방향별 자동차 경로가 모두 카카오에서 계산되는 것을 확인했다. 일부 후보에서 경로 오류가 나와 해당 후보를 다른 공식 실제 주소로 바꿨다. 최종 시작점 선택과 순서 생성은 위 수동 절차에서 실행한다. 서버는 실제 로컬 PostgreSQL·Auth·API를 사용하며 배정 성공을 화면에서만 흉내 내지 않는다. 이번 연습 범위는 영업 진행·순서·공동 배정·휴대폰 조회와 배정 묘지에서의 사진 보고이다. 사진은 별도 로컬 저장소를 사용하며 문자·입금·운영 R2는 준비 대상이 아니다.

운영 서버 업데이트와 실제 핸드폰 설치는 수행하지 않았다. 테스트 뒤 운영 적용 전에는 운영 서버의 현재 권한·스키마 차이를 따로 확인한다.

배정 작업의 주소를 터치하면 카카오 위성 지도와 위치가 고정된 사진 보고를 엽니다. 테스트 사진은 별도 로컬 저장소에만 업로드하며, 사장님 휴대폰 확인에는 `persist:workflow-owner` 세션을 사용할 수 있습니다. 카카오디벨로퍼스의 JavaScript SDK 도메인에 `http://127.0.0.1:55331`을 등록하고 카카오맵 사용 설정을 ON으로 해야 실제 지도를 확인할 수 있습니다.
