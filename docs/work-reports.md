# 작업 보고와 R2 사진 저장소

## 현재 구현 범위 (2026-10-26)

- 작업 사진은 일반 작업자가 휴대폰 **배정 작업 → 묘지**에서만 올립니다. 위치는 배정된 묘지로 고정되고, 올리면 그 곳은 **보고 완료**로 옮겨집니다.
- 사진이 올라오면 그 묘지의 그해 청구서가 서버에 생깁니다(한 묘지에 한 해 하나). 청구 문자·입금·최종 문자 흐름은 [휴대폰 설치와 자동 공유](sync.md)의 "실제 업무 흐름"을 따릅니다.
- 사장님·마스터·부마스터 휴대폰의 **작업 확인**은 청구 문자를 아직 안 보낸 청구서 목록이며, 청구서를 열면 그 묘지·연도의 보고 사진을 받아 문자에 첨부할 수 있습니다. **작업 현황**은 시트별 진행(보고 완료/미완료)입니다.
- PC에서는 **청구·입금** 화면의 청구서 상세에서 보고 사진을 보고, 잘못 올린 보고를 삭제합니다. 데스크톱 고객 상세 아래에서도 해당 묘지의 작업 사진을 볼 수 있습니다.
- 보고 목록과 사진은 회사 신호로 갱신되며 주기적인 전체 조회는 하지 않습니다. 사진은 선택한 보고만 가져옵니다.
- 휴대폰 갤러리 원본은 지우지 않습니다. 같은 묘지의 최신 완료 보고 2건만 R2 사진을 보관합니다.

## 저장 방식과 용량

실제 JPEG 파일은 비공개 R2 Standard 버킷, 위치·보고자·사진 ID·용량은 Supabase에 저장합니다. 고객·청구 데이터는 기존 Supabase를 유지합니다. R2 비밀 키는 Supabase Edge Function의 Secrets에만 넣습니다.

앱은 사진을 긴 변 1600px 이하로 줄여 JPEG로 저장합니다. 보고당 1~10장, 압축 후 장당 1,000,000바이트 이하입니다. 작업 보고의 사진은 앱 안의 사본으로 문자에 첨부하므로 갤러리에 저장하지 않아도 됩니다. 업로드나 문자 발송 후에도 휴대폰 갤러리 원본을 지우지 않습니다. 문자 발송 여부와 별개로, 같은 묘지의 최신 완료 보고 2건만 R2 사진을 보관합니다. 세 번째 보고의 모든 사진 검증과 등록이 완료되면 가장 오래된 보고의 사진을 삭제합니다. 보고 이력과 청구·입금 기록, 휴대폰 원본과 이미 만든 문자 초안의 사진 사본은 유지됩니다.

사진 보관 묶음은 회사·작업공간·묘지 ID로 구분합니다. 공백/유니코드 표기를 제외한 현재 고객 주소와 같은 위치에 남은 과거 보고의 확정된 묘지 ID를 함께 비교합니다. 두 근거가 하나의 현재 존재하는 묘지 ID로 확인되면 연결하므로 고객 주소를 수정한 뒤에도 예전 작업 파일 주소의 보고가 같은 묶음을 이어갑니다. 주소 중복, 과거와 현재 연결 충돌, 묘지 삭제, 연결 근거 없음은 추측하지 않고 사진을 보존합니다. 새로운 보고는 등록 완료 시각 순서로 판단하며 재시도는 순서를 바꾸지 않습니다. 기존 보고는 최초 배포 때 작성 시각을 사용합니다.

`report-photo-retention.sql` 재적용 시 누락된 묘지 연결을 복원하고 확실히 연결된 묘지의 최신 2건을 벗어난 보고를 정리 대상으로 표시합니다. 기존 R2 사진 삭제로 이어지므로 적용 전에 대상과 보관 기준을 확인합니다. 보고 원문·사진 메타데이터·등록 시각·청구·입금 이력은 유지합니다. 삭제 대상은 DB에 기록하고 R2 객체를 모두 삭제한 뒤 예약 용량을 반환합니다. 부분 실패는 다음 보고 조회·등록 때 회사 범위 안에서 재시도합니다. 기존 업로드 URL(5분)로 파일이 다시 생기지 않도록 보고 등록 후 최소 6분이 지난 사진만 실제 삭제합니다. 짧은 시간에 연속 등록한 경우 다음 조회/등록 때 정리되며 별도 폴링이나 스케줄 서버는 사용하지 않습니다. 사진이 삭제된 보고에는 보관 종료 안내를 표시하고 해당 사진으로 문자 준비를 막습니다. 고객 상세 사진에는 보관 중인 보고만 표시합니다.

전체 보고의 예약 용량 합계가 8GB를 넘으면 새 업로드를 거절합니다. 실패한 업로드도 예약에 포함하고, 기기에 남은 초안의 **등록 재시도**로 같은 보고를 완성합니다. 미완료 보고는 다른 직원의 목록에 나타나지 않습니다. 초안은 회사와 로그인 사용자별로 기기에 보관합니다. 미완료 예약/사진의 자동 삭제는 없습니다.

8GB 제한은 이 앱의 보고 용량 보호이며 **Cloudflare 계정 전체 요금을 차단하는 기능은 아닙니다.** 같은 계정의 다른 저장소, API 호출, 별도 서비스 사용량은 별도입니다. 현재 R2 Standard 무료 한도는 10GB-month, 월 Class A 100만 / B 1,000만 회입니다. 초과 사용은 과금되므로 요금 화면도 확인합니다.

## 1. Cloudflare R2 준비

1. Cloudflare 계정으로 로그인 → **Storage & databases → R2 Object Storage**.
2. R2 가입 절차를 완료합니다. 결제 수단/사용량 과금 동의가 표시되면 무료 한도를 확인하고 본인이 직접 진행합니다.
3. **Create bucket** → 현재 저장소: `demo-work-photo`, 저장 방식 **Standard**.
4. 공개 접근(`r2.dev`, Custom domain)은 켜지 않습니다.
5. R2 API 토큰을 생성합니다. **Object Read & Write**, 이 버킷만 허용합니다. Account ID, Access Key ID, Secret Access Key를 확보합니다. 채팅이나 소스에 붙여 넣지 않습니다.
6. 버킷 Settings → CORS policy에 `config/r2-cors.json` 내용을 넣습니다. Android(`https://localhost`), iPhone(`capacitor://localhost`), 데스크톱(`demo://field`), 로컬 미리보기(8091)를 허용합니다. 앱 주소가 달라지면 실제 Origin을 추가합니다. CORS는 인증을 대체하지 않으며 버킷은 계속 비공개입니다. iPhone에서 목록은 보이지만 사진을 열 때 `Load failed`가 나오면 실제 버킷 CORS에도 iPhone 주소가 포함되어 있는지 확인합니다. 이 설정 수정은 앱 재설치 없이 적용됩니다.

## 2. Supabase 연결

기존 회사 프로젝트에서 진행합니다.

1. SQL은 [SQL 적용과 검증](sql-application.md)의 install/upgrade 절차로 적용합니다. 과거 SQL 파일을 하나씩 SQL Editor에 붙여넣지 않습니다.
2. Edge Functions → Secrets에 다음 값을 저장합니다.

| 이름                   | 값                            |
| ---------------------- | ----------------------------- |
| `R2_ACCOUNT_ID`        | Cloudflare Account ID         |
| `R2_BUCKET`            | 만든 버킷 이름                |
| `R2_ACCESS_KEY_ID`     | 해당 버킷용 Access Key ID     |
| `R2_SECRET_ACCESS_KEY` | 해당 버킷용 Secret Access Key |

3. **work-reports** 함수를 배포합니다. 대시보드 편집기를 쓰면 `node scripts/build-server-function.cjs work-reports`로 생성한 `artifacts/server/work-reports/index.ts` 전체를 함수의 `index.ts`에 붙여넣습니다. CLI는 저장소 루트에서 프로젝트 연결 후 `supabase functions deploy work-reports --no-verify-jwt`로 배포합니다. 원본 `supabase/functions/work-reports/index.ts`는 `src/server/work-reports-handler.mjs`와 `report-photo-retention.mjs`를 가져오므로 대시보드에 원본 한 파일만 복사하지 않습니다.
4. Legacy JWT 검증은 끕니다. 이 함수는 직접 `auth.getUser()`와 `demo_access`로 로그인, 활성 회사 소속과 역할을 검증합니다. 인증 검사를 생략하는 공개 함수가 아닙니다.

서명 URL은 5분간 유효합니다. 파일명은 서버가 회사/보고/사진 ID로 결정하고, 업로드 크기·JPEG 종류를 서명에 포함합니다. 모든 사진의 실제 크기와 종류를 R2에서 확인한 뒤 보고를 회사에 공개합니다. 계정 권한 변경은 다음 API 요청부터 반영되며, 이미 받은 사진과 유효한 서명 URL은 즉시 회수되지 않습니다.

## 3. 실제 확인

1. PC에서 테스트 시트를 작업자 계정에 배정하고, 휴대폰 일반 작업자 로그인 → **배정 작업** → 묘지에서 테스트 사진 1장을 등록합니다.
2. 다른 기기의 마스터·부마스터 로그인 → **작업 확인**을 열어 둔 상태에서 그 묘지의 청구서가 자동으로 나타나는지 확인합니다. 일반 작업자에게는 작업 확인·청구 메뉴가 없어야 합니다.
3. 청구서를 열어 사진·전화번호·금액을 확인합니다.
4. 실제 문자 발송은 의도한 테스트 수신 번호로만 직접 실행합니다.
5. 인터넷을 끊고 등록 실패 후 다시 연결해 등록 재시도했을 때 중복 보고가 생기지 않는지 확인합니다.

휴대폰은 `npm --prefix mobile run android:sync` 후 새 APK 빌드/설치가 필요합니다. 소스 또는 웹 리소스 동기화만으로 기존 설치 앱이 업데이트되지는 않습니다.

공식 문서: [R2 요금](https://developers.cloudflare.com/r2/pricing/), [서명 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [CORS](https://developers.cloudflare.com/r2/buckets/cors/).

## 배정 작업 상세와 서버 적용

배정 묘지를 누르면 저장된 KML(또는 승인된 현장·공공 필지) 좌표로 지명·도로명·상호 레이블을 끈 카카오 위성 지도(SKYVIEW)를 열고 같은 화면에 기존 사진 보고 입력을 표시합니다. 좌표가 없으면 위치 확인 안내를 표시하며 주소 대표 위치를 실제 묘지 핀으로 대체하지 않습니다. 고객 검색은 생략하고 초안은 계정·시트·작업별로 보관합니다.

추가 서버 버전은 `20261018-work-task-reports`입니다. 기존 불변 배포본을 수정하지 않고 `20261018-work-sheets` 다음에 적용합니다. 생성된 업그레이드/검증 SQL을 사용하고 `work-reports` Edge Function도 함께 배포해야 합니다. 사장님·마스터 조회에만 고객·묘지 연결 번호를 반환하며, 작업자에게는 주소·순서·좌표와 보고에 필요한 작업 참조만 전달합니다. 고객 삭제 시 직접 연결된 사진도 기존 개인정보 정리·최근 2건 사진 보관 절차를 따릅니다.

맥의 과천 테스트는 `scripts/workflow-test/report-service.cjs`의 별도 로컬 사진 저장소를 사용합니다. 실제 보고 처리기와 로컬 인증·SQL을 거치며 운영 R2에 업로드하지 않습니다. 가상 작업 사진과 보고 이력은 `artifacts/workflow-test` 및 해당 테스트 DB에만 남습니다.

## 작업 안내와 마스터 작업 현황 (2026-10-19)

작업자의 **배정 작업 → 묘지 상세**는 기존 위성 지도 아래에 **고객 요구사항**과 **특이사항**을 표시합니다. 배정된 묘지에 연결된 고객의 `memo`와 `special_notes`만 조회하며, 비어 있으면 ‘등록된 내용 없음’으로 표시합니다. 고객명·연락처·금융 자료와 내부 고객/묘지 번호를 작업자 상세 응답에 추가하지 않습니다. 글 안의 줄바꿈은 유지하며 HTML로 해석하지 않습니다.

사장님·마스터에게는 같은 메뉴가 **작업 현황**으로 표시됩니다. 설정의 **휴대폰 연동** 창에서도 사용할 수 있습니다. 시트별 담당자, 전체·완료·남은 작업 수와 순서별 주소를 조회합니다. 공동 배정한 사람 중 한 명이라도 해당 작업과 정확히 연결된 사진 보고를 등록 완료(`ready`)하면 그 작업을 1건 완료로 집계합니다. 업로드 중인 보고, 주소만 같은 다른 작업의 보고, 다른 회사의 보고는 포함하지 않습니다. 같은 작업의 보고가 여러 건이면 완료 수는 늘리지 않고 최신 보고를 엽니다. 완료 행은 기존 보고 사진·문자 준비 화면으로 연결됩니다.

서버 후속판 `20261019-work-progress`와 보완판 `20261019-work-progress-safety`를 `20261018-work-task-reports` 다음에 순서대로 적용합니다. 2026-10-19 운영 서버에 두 판을 적용하고 최종 버전·해시 검증을 완료했습니다. 새 조회 API `demo_desktop_work_progress`는 로그인 세션을 검증한 사장님·마스터만 호출할 수 있습니다. 기존 회사의 로컬 발행 카탈로그와 공동 DB 방식 모두 지원하며 회사 모드를 전환하지 않습니다. SQL 후속판 적용 후 최신 모바일 화면과 APK를 배포합니다. 이 변경은 기존 `work-reports` Edge Function 재배포를 요구하지 않습니다.

삭제 동기화의 기기 정리 전에 배정 화면의 해당 작업과 진행 중 요청을 무효화하므로, 정리가 끝난 뒤 도착한 응답으로 삭제된 안내문을 다시 표시하지 않습니다. 마스터의 재배정 필요 판정은 작업자와 동일하게 시트 버전·순서 기준·기존 카탈로그의 유효성을 검사합니다.

## 저장소 구조와 자동 정리 (개인정보 보호 모드 회사)

2026-10-22 설계(`docs/superpowers/specs/2026-10-22-r2-storage-lifecycle-design.md`)를 구현한 내용입니다. 개인정보 보호 모드 회사에만 적용하며, 이전에 올린 사진·KML은 예전 경로(`{owner}/{workspace}/{보고}/{사진}.jpg`, `earth/…`)를 그대로 씁니다. 위의 "최근 2건 보관"·"자동 삭제는 없습니다" 설명은 이 모드에서는 아래 규칙으로 바뀝니다.

- **경로**: 정식 파일은 `{회사}/묘지/{사업지역}/{시군}/{묘지번호}/작업사진|위치/…`에 둡니다. 묘지를 정하지 못한 보고는 `{회사}/미연결/작업사진/…`, 업로드 중 임시 파일은 `staging/{회사}/…`입니다. 서버가 DB의 사업지역·주소·묘지번호로 경로를 만들고, 실제 키는 `stored_objects`에 예약합니다. 먼저 예약한 키가 이기므로 재시도나 동시 요청도 같은 경로를 씁니다. 묘지 지역을 나중에 고쳐도 이미 저장한 파일은 옮기지 않습니다.
- **자동 삭제**: 교체되거나 지워진 사진·KML은 6분 대기 후 사람이 분류하지 않아도 자동으로 R2에서 삭제합니다. 사람이 **증빙**으로 표시했거나 다른 곳에서 참조하는 파일은 남깁니다. 현재 NAS 백업이 없으므로 삭제한 파일은 복구할 수 없습니다.
- **미완료 예약**: 업로드를 시작만 하고 7일 동안 끝내지 못한 보고는 만료로 정리하고 예약 용량(8GB 예산)을 돌려줍니다. 기기의 초안은 새 예약으로 다시 올릴 수 있습니다. 검토 대기 중인 KML 요청은 자동 정리하지 않습니다.
- **저장소 점검**: 설정의 **저장소 상태**에서 사장님·마스터가 **저장소 점검**을 누르면 서버가 R2의 이 회사 폴더 목록과 DB를 대조합니다. 기록은 있는데 R2에 없는 파일(누락), 기록에 없는 파일(고아, 7일이 지난 것을 따로 셈), 규칙에 없는 최상위 폴더·파일을 세어 보여 주며, 파일은 지우지 않습니다. 목록이 2만 개를 넘으면 일부만 확인하고 누락은 보고하지 않습니다. 결과는 개수·상태만 저장하고 사진·KML 내용이나 고객 정보를 남기지 않습니다. 정기(주 1회) 자동 실행과 고아 자동 삭제는 NAS 백업을 정한 뒤 켭니다.
- **저장소 상태 화면**: 작업 사진 장수·용량, Google Earth 원본 개수, 삭제 대기 건수, 보존 표시 건수와 마지막 점검 결과를 보여 줍니다. 예전의 파일별 분류 선택은 없어졌습니다.
